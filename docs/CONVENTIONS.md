# Huskyteers Portal — engineering conventions

Team communication app for FTC 19516 The Huskyteers (Anaheim, CA). ~30–40 users.
**English only** (no i18n, no Chinese text in the UI).

Stack: Next.js 16 App Router (Server Components + Server Actions) · React 19 · Tailwind v4 · Prisma 7 (`prisma-client` generator, `@prisma/adapter-pg`) · PostgreSQL · zod 4 · vitest.

> Next.js 16 differs from older versions. Check `node_modules/next/dist/docs/` when unsure
> (e.g. `proxy.ts` replaced `middleware.ts`; `params`/`searchParams` are Promises; `PageProps<'/route/[id]'>` and
> `LayoutProps` are global types generated by `next typegen`).

## Local environment

- Postgres: `npm run db:start` (embedded Postgres on port 54329; already running during development). Dev DB = `portal`.
- `npm run typecheck` (runs `next typegen` + `tsc`), `npx eslint <paths>`, `npm test` (vitest).
- **Never** run `prisma migrate reset`, drop databases other than your own test DBs, or change `prisma/schema.prisma`.
  If you truly need a schema change, stop and report it.
- Don't run `next build` or `next dev` concurrently with other agents unless told to; typecheck + lint + vitest are enough.

## Roles & permissions (source of truth: `src/server/permissions.ts`, mirrored in `src/server/scopes.ts`)

| Role | Subteam | Needs admin approval | Scope |
|---|---|---|---|
| MEMBER | required: SOFTWARE / BUILD / BUSINESS | no (ACTIVE on sign-up) | own checklist, ask questions |
| SOFTWARE_LEADER / BUILD_LEADER (×3) / BUSINESS_LEADER | implied by role | yes | manage own subteam: tasks, review, answer questions (the Business leader also creates whole-team tasks) |
| CAPTAIN | none | yes | all subteams + whole-team tasks |
| MENTOR / TEACHER | none | yes | all subteams + whole-team tasks |
| `isAdmin` flag (**owner**, shown as "Owner") | any role | — | everything above + owners' accounts + granting Owner |

- **Admin access** (`canAdminister`) = every leader, the captain, mentors, teachers, and owners: the Admin area (approve sign-ups and member resources, manage people, email log). It does **not** widen task scope — subteam leaders still only manage their own subteam's tasks.
- **Guardrails on admin access** (`ROLE_RANK`: members < subteam leaders < captain/mentors/teachers < owners):
  non-owners manage only ACTIVE accounts ranked **below** them and sign-ups waiting for approval **up to** their own rank
  (`canManageAccount`), and can only give positions below their own (up to their own when approving a sign-up —
  `canGrantRole` / `grantableRoles`). They never see password-reset links (email only), never change someone else's
  email, can't change their own position, and never touch owners' accounts or the Owner flag. The email log is owners-only
  (`canViewEmailLog`, `requireOwnerUser`). There must always be at least one ACTIVE owner.
- **Owners** (`isAdmin`, `isOwner`) can do all of the above for anyone, including other owners.
- `ADMIN_EMAILS` only bootstraps the first owner: while no ACTIVE owner exists, registering/signing in with a listed email makes that account an ACTIVE owner. Afterwards owners are managed in Admin → People (or `npm run admin`).

- **staff** = any leader/captain/mentor/teacher or admin (`isStaff`). **all-scope** = captain/mentor/teacher/admin (`hasAllScope`).
- Seats: `SEAT_LIMITS` in `src/lib/constants.ts` (1 captain, 1 software, 3 build, 1 business leader).
- Everyone (including leaders) can be assigned tasks and has a Today checklist.
- Nobody reviews their own submission unless all-scope.
- Whole-team tasks (subteam null) are created by all-scope staff **and the Business leader** (`canCreateWholeTeamTask`, used
  by `canCreateTask(actor, null)`: fundraising and outreach need everyone). Who may be put on a task depends on the
  task's subteam — `canAssignTo(actor, assignee, taskSubteam)`, mirrored by `assignableUsersWhere(actor, taskSubteam)`:
  all-scope staff anyone ACTIVE; the Business leader anyone ACTIVE on whole-team tasks and Business people on Business
  tasks; other subteam leaders their own subteam's people. Whole-team tasks are managed (edited, deleted, reviewed,
  finished) by all-scope staff and **whoever created them** (`canManageTask`: so the Business leader manages the ones
  they made, not the captain's). Nobody can edit a task out of their own hands: `updateTask` refuses a subteam the actor
  wouldn't manage it in afterwards (`canManageTask` on the result — e.g. the Business leader making the captain's Business
  task whole-team), and the edit form only offers those (`getTaskFormOptions(actor, { createdById })`). Questions about
  such a whole-team task go to its poster by default (`getAskAboutTask(...).poster`: a whole-team task created by
  someone who isn't all-scope; the ask form preselects "<name> — posted this task" instead of the captain). The
  whole-team **categories** stay all-scope only (`canManageCategories`): the Business
  leader picks from them, and the task form's "New category…" is only offered where `newCategorySubteams` allows it
  (`resolveCategory` refuses it otherwise). **Subteam leaders also review their own members' items** on whole-team tasks
  (`canReviewAssignment(actor, task, { userId, assigneeSubteam })`, mirrored by `reviewableAssignmentsWhere` / `reviewQueueWhere`).
- `getAssignableUsers(actor)` lists everyone the actor may put on *some* task they can create; for the Business leader the
  people outside Business are marked `wholeTeamOnly`, and the task form hides them while the task is for a subteam
  (anyone already picked stays listed with a note, so nothing is dropped silently; `assertAssignable` then says
  "… isn't in Business — make it a whole-team task to add them", and the picker hints "Need people from other subteams?
  Choose Whole team."). `prefillSubteam` (`src/lib/task-prefill.ts`) starts a `?people=` task as whole-team when a
  prefilled person only fits one — even over an explicit `?subteam=` that couldn't take them.
- Members only see their own questions; staff see questions in their scope.
- **Every service must enforce permissions itself** by calling functions from `permissions.ts` (or filtering with `scopes.ts`). UI hiding is not security.

## Checklist lifecycle (`src/server/domain/assignment.ts`)

`Task` = what a leader assigns (title, description, subteam|null, dueDate DATE, priority, creator; `completedAt`/`completedBy` once marked finished).
`TaskAssignment` = one person's checklist item for a task: `TODO → SUBMITTED → APPROVED` (officially done) or `→ REJECTED` (sent back with a note) → `SUBMITTED` again. Members can withdraw `SUBMITTED → TODO`. Managers can reopen `APPROVED → TODO`.

- Use `canTransition` / `allowedFrom` and do **conditional** writes to avoid races, e.g.
  `db.taskAssignment.updateMany({ where: { id, status: { in: allowedFrom("approve") } }, data })` and treat `count === 0` as a `ConflictError`.
- On submit: `status=SUBMITTED, submittedAt=now, submissionNote=note|null` (keep the old `reviewNote` so reviewers can see prior feedback).
- On approve/reject: `status, reviewedById=actor, reviewedAt=now, reviewNote=note|null`. Reject **requires** a note (tell them what to fix).
- On withdraw: `status=TODO, submittedAt=null, submissionNote=null`. On reopen: `status=TODO`, clear `reviewedAt/reviewedById`, keep `reviewNote`
  (and clear `finishedWithTask` / `statusBeforeFinish`, below).

### Marking a whole task finished (`finishTask` / `reopenTask` in `services/tasks.ts`)

For when the job is done but not everyone checked it off. Anyone who `canManageTask` — on the manage page and on
`/tasks/[id]` (`FinishTaskControls`: a `<dialog>` that names who isn't approved yet; focus moves to the button that
replaces it and a `role="status"` line says what happened).

- **Count it as done for everyone still on it** (`credit: "everyone"`, the default): one `UPDATE` turns every item that
  isn't APPROVED into APPROVED with `reviewedById = actor`, `reviewedAt = now`, `finishedWithTask = true`, and
  `statusBeforeFinish` = what it was. `reviewNote` is left alone (pages label it "Earlier feedback" and say "marked done
  with the whole task" from the flag). Like reviewing, a **subteam leader's own item isn't counted** (all-scope staff's is):
  it stays as it is (so it's closed), and the dialog says so. While that own item is **checked off** (SUBMITTED) this choice
  is a `ConflictError` ("Your own item is waiting for review…") and the dialog disables it: a finished task's waiting
  items leave every review queue, so nobody would ever be asked to approve it. They get it approved first, or just close.
- **Just close it — no credit** (`credit: "none"`): items stay as they are.
- Either way `Task.completedAt / completedById` are set, in **one transaction with the task row locked** (`FOR UPDATE`);
  finishing a finished task is a `ConflictError` naming who did it. No emails.
- **Reopen task** (same people, same lock): clears `completedAt/completedById` and puts back only items still APPROVED
  with `finishedWithTask` (status = `statusBeforeFinish`, review fields and both flags cleared). Items reviewed one by one
  stay. Reopening an open task is a `ConflictError`. Its confirm only promises to put people back when someone was
  counted (`counted` / `BoardTask.countedWhenFinished`).
  **Known loss:** finishing overwrites `reviewedById/reviewedAt`, and nothing stores the old ones, so a **sent-back** item
  restored by Reopen task keeps its note but loses who sent it back and when (the member's card shows the feedback
  without "— name", the manage page says "Feedback", and it drops out of the overview's Recent activity). Restoring them
  exactly needs a migration (e.g. `previousReviewedById/previousReviewedAt` next to `statusBeforeFinish`).
- **While finished**: anything not APPROVED is **closed** (`isClosedItem`): no credit, off Today and the Open tab (listed
  under Done as "Closed — the task was marked finished" with the dashboard's minus-circle mark; the Done tab is ordered
  by when each item was done — approval time, or the finish time for closed ones), never overdue, out of the review queue (`reviewQueueWhere`, so
  the nav badge and bulk approve too). Members can't check off, uncheck, or edit the note (`services/checklist.ts` locks the
  task row `FOR SHARE` first, so a check-off can't land after the finish), nobody signs up or leaves (`canSignUpForTask`,
  `leaveTask`), and sign-ups can't be opened (`setSignupOpen`). Such a refused check-off / uncheck / note is a
  `ConflictError` with `code` = `TASK_FINISHED_CODES.counted | .closed` (`src/lib/action-state.ts`, passed on as
  `ActionState.code` by `runAction`) and a message saying how it ended ("Marcus Johnson marked the whole task finished —
  it counts as done for you."); the checklist item shows it as a neutral status line in place (no refresh, which would
  usually take the item off the list), focused. Managers can still **approve** a closed submission on the task page (then
  it counts), not send it back. On a finished task the per-person "Reopen" is **Take back credit** (`ReopenItem`, with a
  confirm and a status line): `reopenAssignment` (which returns `taskFinished`) takes that person's credit back for good —
  the item is closed ("Doesn't count — the task was marked finished without it"). Editing still works, but nobody new can
  be added (the picker disables everyone not already on it). Duplicating makes an open task; deleting works as usual.
- **Counts**: approved items count as approved everywhere (progress, the two-week report's "what got done" at the finish
  time). Closed items stay in totals (so completion rates stay honest) as their own `closed` bucket, never as to do /
  waiting / overdue: Manage → Tasks and the task page (`StatusCounts.closed`), the overview, team and member progress,
  Admin → People (`closedAssignments`), and the dashboard's public status `"closed"`. Recent activity leaves out items
  approved by finishing (one task could fill it).

## Categories, sign-up tasks, and the Task dashboard

- `TaskCategory` groups a subteam's tasks (`subteam` null = whole-team categories), managed by `canManageCategories`
  (= `canManageSubteam`) in `services/categories.ts` (writes to one subteam's list take an advisory lock: names are unique
  per subteam, case-insensitively, max `LIMITS.categoriesPerSubteamMax`). A task's category must belong to its subteam.
- A task is either **"Assign people"** (`signupMode = false`) or **"Let people sign up"** (`signupMode = true`, optional
  `signupLimit` = most people on it, counting everyone). `signupOpen` closes/reopens sign-ups without changing the mode
  (`setSignupOpen`); editing a sign-up task keeps it open/closed as it was. Switching to "Assign people" clears `selfAssigned`.
- `services/signups.ts`: `signUpForTask` / `leaveTask`. Sign-ups and task edits lock the task row (`SELECT … FOR UPDATE`)
  before counting people, so the limit holds under races. Leaving is only for your own self sign-up while it's TODO.
- `updateTask` gets `previousAssigneeIds` (+ `previousAssigneeIdsSent`) from the edit form: changes are computed against the
  people the form showed, so sign-ups that happened while the form was open are kept.
- `/tasks` (Task dashboard) and `/tasks/[id]` are for every ACTIVE user (`queries/board.ts`). They show who's on each task
  with a **public** status only (done / checked off / to do — "sent back" shows as to do; closed on a finished task) and
  never notes. A task marked finished is always on **Past** (`activeWhere` requires `completedAt: null`), shows a
  "Finished" badge, and reports `signupOpen: false`. A section's `canManage` (its categories) and `canCreateTasks`
  (`canCreateTask`) are separate: the Business leader gets "New task" on Whole team without the category controls.

## Team members (`src/server/queries/people.ts`, `/people`)

"Team members" (first item of the menu's Team section) is the read-only team directory for every ACTIVE user:
avatar, name, position ("Build Leader", "Software member"), email as a `mailto:` link, the Owner badge, and last seen
(`lastSeenLabel`, the same as Admin → People), by name. `listTeamMembers` requires an ACTIVE viewer, lists **only ACTIVE
accounts** (sign-ups waiting for approval, turned-down and disabled accounts stay admin-only in Admin → People), and
selects only `id, name, email, role, subteam, isAdmin, lastSeenAt` — never the password hash, sessions, approval info, or
email preferences; it stops at `TEAM_MEMBERS_MAX` (300) and counts everyone, then sorts by name with `Intl.Collator`
(the database's C collation would put "jason" and "Élodie" after "Zara"). Search (`?q=`) matches name or email, or a
word of the position as shown (`describeRole`: "build", "mentor", "software member"; 3+ letters) — `cleanSearchText`
drops control characters (a NUL byte makes Postgres fail the page) and `escapeLike` makes `%` / `_` literal
(`src/lib/search.ts`; Prisma's `contains` doesn't escape them). `?role=` / `?subteam=` filters (`parseTeamMemberFilters`
drops anything else, e.g. a `status`) apply as soon as they're picked (`AutoSubmitSelect`; the Filter button still sends
the search and works without JS). The filter form is keyed by the filters, so "Clear filters" and the menu link (client
navigations) reset the menus too — same for Admin → People. Phones get stacked cards ("Seen 6 h ago" / "Never signed
in" on its own line). Members get no links into Admin; people with admin access get "Manage people in Admin → People",
and a person's name links to `/admin/users/[id]` (with a chevron, and a row hover only on those rows) only when
`canManageAccount` allows it (`teamMemberAdminHref`). What Admin → People shows and who can open it is unchanged.
Avatars show each person's own photo when they have one (see **Members' photos**; the page passes `photoId` with each
row, so `TeamMemberList` stays a plain component).

## Members' photos (`src/server/services/user-photos.ts`, Settings → My photo)

The owner's ask: everyone uploads their own photo in Settings; they can keep it out of the portal, and it goes to the
team website automatically. `UserPhoto` (one per account, `userId @unique`, migration `20261005070000_user_photos`
with the CHECK and the deletion trigger), `User.showPhotoInPortal` and `User.showPhotoOnWebsite` (both default true).
Client-safe constants, messages, the crop math, the public JSON's types, the name key's rule, and the holds' types:
`src/lib/user-photos.ts`.

- **Who**: every ACTIVE account, any position, uploads / replaces / removes **its own** (`uploadUserPhoto`,
  `removeUserPhoto(ctx, {})`); PENDING, REJECTED, and DISABLED accounts are refused (`USER_PHOTO_INACTIVE`, checked
  again inside the save, so an account disabled meanwhile can't save one). People who manage an account
  (`canManageAccount`: owners anyone; others the ACTIVE accounts ranked below them) remove its photo too —
  `removeUserPhoto(ctx, { userId })`, the **Photo** card on Admin → People → a person (`UserPhotoCard`, shown while the
  account is ACTIVE or still has a photo), because the photo goes public on its own — and that also **holds** the
  account's photos off the website (below), so the same picture can't go straight back up. Uploads and removals:
  `USER_PHOTO_CHANGES_PER_HOUR` (20) per person (`user-photo:<id>`), refused with `RateLimitError(
  USER_PHOTO_RATE_LIMITED_MESSAGE)` ("You've changed your photo 20 times in the last hour…": no field error — the
  Settings card shows anything that isn't about the picture as an alert, not on the file picker); the switches aren't
  limited.
- **The picture**: the Settings card (`MyPhotoEditor`) refuses HEIC (the posters' iPhone hint) and anything not
  PNG/JPG/WebP before reading it (`userPhotoProblem`), draws it as the round avatar it becomes (drag or arrow keys to
  move, a Zoom slider / buttons / `+` `−`; `photoCropRect` / `movePhotoCrop` / `clampPhotoCrop`: a square of the
  short side ÷ zoom, never outside the picture), and sends a `USER_PHOTO_SIDE` (512) square JPG (quality 0.86, white
  behind transparency; `loadPicture` / `toJpeg` from `components/posters/shrink-picture.ts`) — never the original. The
  server checks it regardless (`checkUserPhoto`), **tighter than posters** because every avatar in the portal and on
  the public site downloads and decodes the whole photo: ≤ `USER_PHOTO_MAX_BYTES` (1 MB; `userPhotoTooBigMessage`),
  PNG/JPG/WebP by its bytes (HEIC: the hint; a real GIF/PDF/SVG or a file that doesn't claim to be a picture:
  `USER_PHOTO_TYPES_MESSAGE`; one that claims to be but isn't: "couldn't be opened"), ≤ `USER_PHOTO_MAX_DIMENSION`
  (1,024) pixels a side (`userPhotoTooLargeMessage` — a 7,000 × 7,000 PNG is ~200 MB decoded), a still picture
  (`isAnimatedImage`: APNG acTL/fcTL/fdAT, WebP's animation flag or ANIM/ANMF → `USER_PHOTO_ANIMATED_MESSAGE`),
  **metadata stripped in strict mode** (`stripImageMetadata(…, { strict: true })`: GPS, camera, author, comments, and
  also colour profiles — JPEG APP2 ICC, PNG iCCP, WebP ICCP — a JPEG's JFIF thumbnail / JFXX (APP0 becomes a bare JFIF
  header, APP14 a bare Adobe one), and every PNG chunk the picture doesn't need (sPLT palette names, hIST, bKGD,
  animation); a JPEG/PNG's orientation kept, width/height swapped for 5–8), and a JPEG only with markers browsers draw
  (`jpegMarkersDrawable`: SOF0–2, DHT, DQT, DAC, DRI, SOS, RSTn, APPn, COM — a JPGn, DNL, lossless, hierarchical, or
  arithmetic frame → "couldn't be opened"). Stored as `photo.<ext>` (never the uploaded name). Stored file kind `photos`
  (`withStoredFiles`, Postgres or R2) under the shared cap (`FileStorageUsage.photos`, "of members' photos";
  `userPhotoStorageFullMessage`); no per-person allowance (one small photo each). A new photo is a **new row** (new id,
  so every cached copy of the old one is a different address): the old row is deleted in the same transaction (the
  trigger queues its R2 object), and the actions call `scheduleFileCleanup()` (also after deleting an account, whose
  photo cascades).
- **Switches** (`updatePhotoVisibility(ctx, { which: "portal" | "website", show })`, your own account only, saved as
  soon as they're flipped — `AutoSaveSwitch`, which `PublicProgressSwitch` also uses; `held` in the answer when the
  website switch went on but a hold keeps it off): *Show my photo in the portal* (off: the team sees initials — the
  person still sees it in Settings, and people who manage their account in Admin, who decide what goes public; the copy
  says so, and that it doesn't change the website) and *Show my photo on the team website (public)* (the copy says the
  site is public, that the photo is public while it's on — next to their name wherever the website lists them, found
  by full name, and openable by anyone whether or not they're listed — that it's on automatically, and that turning it
  off takes it off within a few minutes; it also says so when the team has photos turned off). Under the saved photo
  the card says where it shows (`MyPhotoVisibility`: "Hidden in the portal: the team sees your initials instead.", "On
  the team website (public).", "Not on the team website: your switch below is off.", held, or the team shows none),
  since the preview itself always shows it.
- **Holds** (`src/server/queries/website-photo-holds.ts`; one TeamNote row per held account, key
  `website-photo-hold:<userId>`, body `WebsitePhotoHold` JSON — no schema change; a body that can't be read holds as
  `kept-off`): a held account's photo is off the website (the JSON and its address) **whatever its own switch says**,
  and stays in the portal. `renamed` — you changed your own name in Settings (`updateProfile` →
  `holdWebsitePhotoAfterRename`, only when `teamPhotoNameKey` changes — not case, spacing, or accents — and whether or
  not you have a photo yet, so renaming first and uploading after doesn't skip it; `from` = the name before, kept
  across further renames; renaming back to it lifts the hold; `updateProfile` returns `photoHeld` and Settings says
  so): the website matches photos by name and members can change theirs freely, so otherwise anyone could put a
  picture on someone else's card (a coach, an alumnus) or knock theirs off. `removed` — someone who manages the account
  removed its photo (`byName`). `kept-off` — someone who manages the account keeps it off (`keepPhotoOffWebsite`, e.g.
  no photo release; can be set before any photo). `allowWebsitePhoto` lifts any of them. Both: people who manage the
  account, never their own unless they're an owner (`USER_PHOTO_HOLD_OWN` — a leader can't wave their own new name
  through), `USER_PHOTO_CANT_HOLD` otherwise; admin actions `keepPhotoOffWebsiteAction` / `allowWebsitePhotoAction`
  on the Photo card (`getManagedWebsitePhotoHold`: `{ hold, canChange }`). A hold someone put on (`removed`,
  `kept-off`) isn't replaced by a rename. Settings shows the person a warning (`websitePhotoHoldSentence`).
- **Admin → Approvals → Members' photos** (`WebsitePhotosCard`, `getWebsitePhotoReview(actor, now)`, everyone with
  admin access; shown only when there's something in it): photos go public on their own, so admins get a notice
  instead of an approval step — who's **held off the website** (with a "N to check" badge for renames: check the new
  name, then Allow on their page) and every photo that went **on the website in the last `WEBSITE_PHOTO_RECENT_DAYS`
  (7) days**, newest first (≤ 30 each), names linking to the person for those the viewer manages (their Photo card has
  Remove, Keep off, Allow); avatars only where the viewer may see the photo in the portal.
- **Avatars in the portal**: `Avatar` (`components/ui/avatar.tsx`, client-safe) takes `photoId`: the photo
  (`/people/photos/<id>`, `alt=""`, lazy, `object-cover`) **covers the initials inside the same fixed circle** — no
  layout shift — drawn by `AvatarPhoto` (`components/ui/avatar-photo.tsx`, a tiny `"use client"` leaf, so `Avatar`
  still works from server and client components): if the photo can't be loaded (a 404 because it was replaced,
  removed, or hidden after the page was drawn, or the sign-in page) it turns `invisible` (`data-failed`), so no
  broken-picture icon covers the initials — also when that happened before hydration (`imageFailed`: complete with no
  picture, checked once it's on the page) — and shows again if it loads after all. The Settings preview and the Photo
  card use it too. The whole avatar stays `aria-hidden` (the name is always next to it). `UserChip` passes `photoId`
  on. Who shows one comes from **one read per page render**:
  `getPortalPhotoMap()` (`queries/user-photos.ts`, React `cache()`: ACTIVE accounts with a photo and
  `showPhotoInPortal`, `Map<userId, photoId>`). Server components use `UserAvatar` / `UserChipWithPhoto`
  (`components/app/user-avatar.tsx`, `server-only`, async: they look the id up); client components get ids in their
  props from the page (`photoIdsFor(map, ids)` → `Record<userId, photoId>`, or `photoId` on the row) — never a join in
  every query. Photos show on: the menu's chip (sidebar and phone drawer) and Settings' profile chip, Team members,
  Admin → People (list, a person, recent decisions), the Task dashboard's people chips and a task's people, Manage
  (a task's assignees, Review, Overview's Needs attention and Recent activity, Progress rows and a person's page),
  Questions (list, a question, its messages), Discussion (a discussion and its replies), Announcements, Orders (list

  Approvals' sign-ups (waiting accounts can't have one).
- **The signed-in route** `src/app/(app)/people/photos/[id]/route.ts` (`getUserPhotoFile`): any ACTIVE viewer while
  the owner is ACTIVE with `showPhotoInPortal`; the owner always (Settings shows it while it's off in the portal); people
  who manage the owner's account (they decide what goes public — the portal switch's copy says they still see it);

## Sponsorships (`src/server/services/sponsorships.ts`, `/sponsors`)

The Business team's sponsor tracker (replaces their spreadsheet). Only the Business subteam and staff can see or change it
(`canUseSponsorships`; pages show everyone else a short explanation, never data); deleting is for whoever added it, the Business leader, and all-scope
staff (`canDeleteSponsorship`; the Business leader and all-scope staff are `canManageSponsorships`). Stages: Haven't started → Do soon → Needs work → Submitted → Accepted / Declined → Finished.
Moving into Submitted/Accepted fills that date with today (team timezone) only if it's empty. `amountReceived` is whole
dollars (`src/lib/money.ts`). "Info for applications" is a `TeamNote` (key `sponsorship-info`, up to `LIMITS.teamNoteMax` = 10,000 characters) — never store passwords in it (the card warns, without blocking the save, when `mentionsPassword` in `src/lib/sponsorships.ts` matches).

planner's `?path=` check) is a 404 before the database is asked (a NUL byte used to be a 500), here and on the Paths

Rules: JSON only, `Cache-Control: no-store`, `nosniff`; ACTIVE people only — everyone else a JSON 401, never a redirect
(the proxy answers `/api/*` without a session cookie with that 401 itself — except `/api/public/*`, see Public
progress, and the daily job's exact path `/api/cron/meeting-audio`, see Meeting recaps); every POST/PUT/DELETE needs
`Content-Type: application/json` **and** `X-Planner: 1`, and when present `Origin` must be this site
(`request.nextUrl.origin`, `APP_URL`, or the forwarded host) and `Sec-Fetch-Site` must be `same-origin` — otherwise 403
before anything is read; bodies are read up to `PLANNER_API_BODY_MAX_BYTES` (300 KB, 413 past it, by `Content-Length`
or while reading) before parsing; data over 256 KB is 413 too. Every request a signed-in person makes counts toward

## Order list (`src/server/services/orders.ts`, `/orders`)

What the team needs to buy (replaces the Business team's "Purchase List" sheet). `PurchaseItem`: description, notes (SKU,
where to find it), an http(s) product link (`https://` added to a bare `andymark.com/…`), vendor, optional quantity
(1–`LIMITS.purchaseQuantityMax`), cost for the whole line in **cents** (`costCents`; typed in dollars and read by
`parseCents` in `src/lib/orders.ts` — the `parseDollars` formats, but keeping the cents, up to $100,000), "For"
(`subteam`, null = whole team), status, orderer. Everyone ACTIVE sees every item and adds items (orderer = themselves).
Managers (`canManageOrders`: everyone with **admin access** — accounts someone approved; the self-chosen Business
subteam is not enough to approve spending) set any status (including **Approve**), edit/remove anything, and pick the
orderer (an ACTIVE person, or no one yet; an edit may keep one who left). **Nobody approves their own request** unless
all-scope: from Requested or N/A, an item a leader added only goes to N/A/Requested for them (`purchaseStatusTargets`),
and only all-scope staff add an item with another status (`canAddPurchaseWithStatus`). Everyone else edits/removes items
they added or order while **Requested** (`canEditPurchase`; conditional writes, so an approval that lands first wins); the
orderer **and the Business subteam** (who buy for the team) move an item one step along Approved → Ordered → Done and
back — never approve, mark N/A, or send it back to Requested. Removing is permanent (the confirm points past-Requested
items to N/A instead). **Out-of-date pages:** the status menu sends `from` (the status it showed) and `seen` (the item's
`updatedAt`); every status write is conditional on the status it was checked on, a stale `from` is refused with
"X just changed it to Y." (never "undo someone's Ordered"), and leaving Requested needs `updatedAt = seen` (nobody
approves an edit they haven't seen). The edit form sends `seen` too: a save over someone else's change is refused once
(`ORDER_EDIT_CONFLICT`, the page refreshes, saving again keeps this version); non-managers' edits never write the orderer.
Every status change writes `statusChangedAt/By` (the item's page shows "Status changed by X · time"). Writes are
rate-limited per person (`ORDER_WRITES_PER_HOUR` 120, adds also `ORDER_ADDS_PER_HOUR` 30). No emails: Today shows
"N approved items for you to order" to orderers and "N items to approve on the order list" to the Business leader and
the captain (`countOrdersToApprove`, not their own requests unless all-scope).
The list (`queries/orders.ts`): Open (Requested/Approved/Ordered, oldest first) / Done / N/A (latest change first) / All
tabs with counts, "For" chips (`?for=SOFTWARE|BUILD|BUSINESS|team`; the chosen chip is scrolled into view on phones),
`?mine=1` (added or ordering), and a summary line for the tab (`orderSummaryText`: open items, waiting for approval, to
order, estimated total of the priced open items + how many have no price, or "No prices yet"; Done: count + total; N/A:
count) that follows the For/Mine filters. Desktop: a table (Notes/Qty/For/Added columns from `xl`, folded into
Description below); phones: cards whose title opens the item's page ("Product page ↗" is its own link, notes clamped
to 3 lines, "Orderer: X"). The status is an inline colored menu (`components/orders/status-select.tsx`, the sponsor stage
menu's 600 ms debounce + flush on leave, the list keeps its order, focus moves on when a row leaves the filter — after a
refused change too, saying why — and to the badge when a refused change turns the menu into one) showing only the
statuses the viewer may pick — a badge when none. **Export to spreadsheet** (`/orders/export`, a route handler, any
ACTIVE user, the page's filters, named after them: `order-list-software-open-2026-09-24.csv`) sends a UTF-8 CSV with the
sheet's first columns (Orderer, Status, Description, Notes, …); `csvCell` puts a `'` before text starting with `=`, `+`,
`-`, `@` (or tab/CR) so a spreadsheet never runs it. After a removal the list shows `?removed=1` ("Item removed.", on the
tab the item was on) — never text from the link.

## Attendance (`src/server/services/attendance.ts`, `/attendance`)

Taking attendance with a rotating QR code, "Coming?" answers, day plans, and two-week reports.

- **Who**: `canRunAttendance` (teachers, the Business leader, the captain, mentors, owners) start / close / reopen
  attendance (the projector QR code and 6-digit code), write "What we did", delete a session started by mistake, and
  change the schedule (`/attendance/settings`). "What we did" and deleting a session more than `ATTENDANCE_EDIT_DAYS` (7)
  days old: only teachers, mentors, and owners (`canFixOldAttendance`, `canEditSessionOn`). **Everyone with admin
  access** (`canFixAttendance` = `canAdminister`: every leader, the captain, mentors, teachers, owners) opens any
  session's page (`/attendance/sessions/[id]`) and fixes who was there **at any time, however old**: adds people by
  hand (`MANUAL`, `markedBy`), takes them off, and changes credits (see Credits) — each change goes into the change log.
  **Never their own**: nobody adds themselves by hand (`NOT_YOURSELF`) or changes their own credit (`OWN_CREDIT`), so
  nobody gives themselves credit without a scan; another admin does it (taking yourself off is allowed, and logged).
  `canPlanAttendance` (all staff) see **Who's coming** (`/attendance/plan`), write a day's plan, and read reports
  (`/attendance/reports`). Everyone ACTIVE checks in and answers "Coming?" for themselves. Members get 404 on session,
  report, and change-log pages (and the CSVs) and are sent back from plan/settings/the reports list.
- **Fixing mistakes**: `deleteSession` removes today's session, or an earlier one nobody checked in to themselves (only
  `MANUAL` records): in one transaction it locks the session row (`FOR UPDATE`, so nobody checks in meanwhile), writes
  the change log (one `SESSION_DELETED` row plus a `REMOVED` row per record), and deletes it (records cascade), so a
  mis-tap doesn't count as "held". Start asks
  first on a day that's neither a regular day nor an extra meeting. "What we did" and day plans send back the
  saved text the form started from (`base`): if it changed meanwhile the save is a `ConflictError` and the form shows
  their text ("Use theirs"); forms that must keep typing (these, the schedule) submit with `onSubmit` + `startTransition`
  so React's form reset can't undo edits.
  Accounts with attendance history can't be deleted (`NO_ACTIVITY` in `services/admin.ts`); disable them instead.
- **Sessions**: `AttendanceSession` is unique per `(date, kind)` — one REGULAR and one FLEX per team-timezone day.
  `openSession` creates today's, reopens a closed one with a **fresh random secret** (old codes stop working), or returns the
  open one unchanged. Check-ins only go into **open sessions of today**; `AttendanceRecord` is unique per person, so a
  second scan returns `already: true` ("You're already checked in ✓"). Someone already on the list **by hand** who
  scans in while it's open becomes a real check-in (`recordCheckIn`, see "Scanning over a hand entry" under Credits).
  "Checked in" (`checkedIn` on Attendance, Today, the scan page) means **checked in myself** with credit: a hand entry
  or No credit isn't, so the Scan / Enter code buttons stay. Closing works on any open session, also one left open from
  an earlier day (its page shows "Still open from …" with Close; Attendance's earlier list marks it "Still open").
- **Codes** (`src/server/attendance/codes.ts`, pure): 30-second slots. QR token = `<sessionId>.<slot base36>.<HMAC-SHA256(secret,
  "qr:<id>:<slot>") first 16 bytes, base64url>`, accepted up to 10 slots old (~5 min, so a sign-in redirect still lands) and
  one slot ahead (clock skew). A forged signature is "invalid", never "expired". The 6-digit code is HMAC-derived per slot
  and accepted for the current slot and 3 before (~1.5–2 min); it's matched against today's open sessions only, attempts
  are rate-limited per person (`CODE_ATTEMPT_LIMIT`, 10 per 10 min; format errors don't count), and all comparisons are
  constant-time. **The secret never leaves the server**: the projector page fetches `{ svg, code, expiresAt, expiresInMs }`
  from `getLiveCodeAction` (runners only, open sessions of today; SVG made with `qrcode`, shown as a `data:` image) again
  right after it runs out (`expiresInMs`, so the browser's clock doesn't matter). Anyone with a fresh link or code checks in:
  the live screen reminds runners to compare "Checked in" with the headcount, and full screen lists the latest names.
- **Scan page** `/attendance/scan/[token]` only **reads** on GET (`getScanLanding`: signature, age, session, already in?);
  `<ScanCheckIn>` sends `checkInWithTokenAction` **once** after mount, so prefetching or reloading never writes. It's the same
  element whether or not I'm already in (`alreadyCheckedIn`, read once on mount), so the refresh after its own check-in
  keeps it mounted and it shows "You're checked in for Regular ✓" (focused). Signed-out people go through the proxy's
  `/login?next=…` and come back; with a stale cookie, `requireActiveUser` builds `next` from the proxy's `x-hk-path`
  request header. The page sets `referrer: no-referrer`.
- **In-app scanner** (`components/attendance/qr-scanner.tsx`): `getUserMedia({ video: { facingMode: "environment" } })`,
  `playsInline muted` video, decoded with `jsqr` (dynamic import) on a canvas ~5×/s, follows only our own
  `/attendance/scan/<token>` links (`attendanceScanPath`: the configured app origin or this page's own, no query/userinfo),
  stops the camera on success, "Stop camera", and unmount. Blocked / missing / busy camera and insecure pages get a clear
  message and **Type the code instead**. `next.config.ts` allows `camera=(self)`.
- **Session page / live screen** `/attendance/sessions/[id]` (every admin; `getRunnerSession`): while it's open today,
  runners get the big QR + code **first** (Full screen at its top, so the projector view is one tap away), and **"Said
  they'd come — not checked in yet (N)"** (see No-shows) sits **folded** under the counts (names only, "Show list" for
  the quick actions: they may still be on their way); once it's closed, "didn't check in" is at the top, open.
  Runners also get Close / Reopen (both inline: focus moves to the other button, a status line says what happened),
  "What we did", and Delete; other admins see "Attendance is open" instead of the code. Everyone there gets the counts
  — **Scanned in** (`scannedCount`: scans and typed codes with credit, what the headcount should match; "+ N added by
  hand" under it, `handCount`) and Said they'd come — and the roster, **On the list** (`router.refresh()` every 10 s
  while it's open and visible) with a credit menu per person offering only what this admin may set on that record
  (at Flex grouped into "Flex" and "Regular credit", `creditMenuGroups`; the admin's own row shows its credit without a
  menu), Remove, "Marked as not here" (No credit) listed apart, search to add anyone ACTIVE but yourself by hand ("People
  you add count as", 1/2 to start), and **History** (this session's change-log rows, newest 50, linking to all
  changes). **Full screen** is a dialog portaled to `<body>` with everything else `inert` (and asks the browser for full
  screen); it shows "N scanned in" and "Just scanned in: …" (scans only, never people added by hand); Esc exits. Past
  sessions open here too: admins get today's and the last 5 on Attendance ("Take attendance" for runners, "Fix
  attendance" for other admins), and the report's dates link to them.
- **Coming?** (`AttendanceRsvp`, one row per person per day): `setRsvp` changes only the fields sent (`regular`
  YES/HALF/NO on regular days, `flex` YES/NO on Flex days — no Half —, `note` ≤ `LIMITS.rsvpNoteMax`; `""` clears one, and
  clearing works on any day). Days from today to `today + LIMITS.rsvpDaysAhead`; **past days are read-only**. An answer
  with nothing left is deleted. The UI saves each tap right away (optimistic, buttons stay enabled, `aria-pressed`,
  a `role="status"` line); tapping the chosen answer again clears it. The list shows every team day people can answer
  for (`upcomingTeamDays`: today to `today + LIMITS.rsvpDaysAhead`, the same days `setRsvp` accepts — about 13 with
  Mon/Tue/Thu, plus extra meetings): 5, then "Show N more days". `/attendance?day=YYYY-MM-DD#day-YYYY-MM-DD` goes
  straight to one day's card (`id="day-…"`, outlined; "Show more days" starts open when it's past the first 5). The Today page shows a compact card for today ("Scan to check in"
  while a session is open, plus "Show code" for runners, and for staff "The … report is ready" in the first
  `REPORT_READY_DAYS` days of a new period).
- **Schedule** (`TeamNote` `attendance-settings`, JSON, read with `getAttendanceSettings(today, db)`, defaults in
  `src/lib/attendance.ts`): regular weekdays (default **Mon, Tue, Thu**), Flex weekdays (default Tue, Thu — the school's
  Flex period), `reportStart` (must be a Monday), and `weeklyTarget` (times a week, default 2 — see Credits below). Two-week report periods run 14 days from it
  (`reportPeriodFor` / `reportPeriodByIndex`); periods before it (attendance taken before "Reports start" moved) get
  **negative indices** (`firstReportIndex`, `parseReportIndex`), so no report is ever hidden. `/attendance/reports/[index]`

  who joined after the period aren't listed —, said yes but didn't come, came without answering — `buildReport` in
  `src/server/attendance/report.ts`), and what got done (checklist items approved, parts marked done,
  notebook entries written — instants filtered by team-timezone day bounds, `startOfDayInTimezone`). Phones get stacked rows
  instead of the tables. Print CSS and a CSV route (`csvCell` quotes `, ; " CR LF` and prefixes `'` to cells starting with
  `= + - @`, tab, or CR; the CSV also lists what got done). Mentors and teachers aren't listed as "No answer" (only when they
  answer or come). "Your attendance" also counts from the day you joined. `/attendance/settings` says "Regular
  meetings: Mon, Tue, Thu", lists the upcoming extra meetings (`getUpcomingExtraMeetings`, each linking to its event),
  and has **Add an extra meeting** (`/calendar/new?kind=MEETING&from=schedule`, for `canManageCalendar`; Who's coming

- **Extra meetings** = Team calendar events of the kind `MEETING` ("Extra meeting"). Every day one covers

  `getAttendanceSchedule` (`queries/attendance-settings.ts`) also load the MEETING events in `extraMeetingWindow(today)`

  weekdays). So members are asked "Coming?" (Yes / Half / No), `setRsvp` / `setDayPlan` accept the day (services pass
  `ctx.db` and their team-timezone today), Who's coming lists it, starting Regular attendance doesn't ask, and Today shows
  "Coming today?". Day cards, Today's card, and Who's coming show
  an "Extra meeting" badge and the event's title linking to it (`RsvpDay.extraMeetings`, `DayCounts.extraMeetings`).
  Reads through the app-wide client share one load per request (React `cache`: the Today page and its card); a

- **Assign a task to the people coming** links to `/manage/tasks/new?people=<id>,<id>&due=<day>&back=/attendance/plan?day=<day>`;

- **Credits and the weekly target** (Gwen's "-/2 times"): each `AttendanceRecord` counts toward a weekly target by its
  `credit`, in **sixths** (6 = 1, 4 = 2/3, 3 = 1/2, 2 = 1/3, so everything adds up exactly), and `creditKind`
  (REGULAR / EXTRA = "EC" / FLEX). The options are `CREDIT_OPTIONS` in `src/lib/attendance.ts` (client-safe): 1, 2/3,
  1/2, 1/3, 1/2 EC, 1 EC, 1/2 Flex, 1 Flex, and **No credit** (0, `NO_CREDIT`: on the sheet but counted as not there —
  admins only). `creditOptionsFor(kind)` = what fits a session (Regular: 1…1 EC; Flex: 1/2 Flex, 1 Flex).
  **Who sets what** (the owner's rules):
  - A member's **own check-in** always needs the scan (QR, typed code, or the in-app scanner). At **Regular** it counts
    as **1**, with nothing to pick (`memberCreditOptions("REGULAR")` is empty; the card says "Regular counts as 1").

  - **EC** ("1/2 EC", "1 EC") only by `canGiveExtraCredit`: the Business leader, teachers, mentors, and owners

  regular / EC / Flex breakdown, `creditBreakdown` → "1 regular · ½ Flex · ½ EC"). Shown as "1⅔ of 2 this week"

## Meeting recaps (`src/server/services/meeting-recaps.ts`, `/meetings`)

The owner's ask: the key points of every important meeting, each named and put in categories, for everyone to read;
only people with admin access record and change them; the recording itself is kept **3 days**, then deleted
automatically. A port of the VoiceCollector recorder: recording, transcription, and the key points' first draft all
happen in the browser (see **Recorder (browser)**); the server stores text and, for 3 days, audio. Client-safe helpers:
`src/lib/meeting-recaps.ts` (limits, audio types, the list's filters, links, labels) and `src/lib/meeting-recorder/*`.

- **Who**: everyone with admin access (`canManageMeetingRecaps` = `canAdminister`; ACTIVE) records, uploads, writes up,
  edits, and deletes recaps, deletes a recording early, and keeps the categories — checked in every service
  (`MEETING_RECAP_FORBIDDEN`) and in the admin queries (`getMeetingRecapFormValues`, `getMeetingRecorderSetup` → null).
  **Everyone ACTIVE** reads every recap and listens to its recording while it's kept. Pending and disabled accounts get
  null / [] from every query and a 403 from the part route.
- **Data** (migration `20261007090000_meeting_recaps`): `MeetingRecap` — `title` (`LIMITS.meetingTitleMax`, 160),
  `meetingDate` (DATE, team timezone; from 5 years back to tomorrow — a saved date may stay when it's out of range
  later), `keyPoints` (≤ 20,000, one point per line) and `transcript` (≤ 300,000, one line per segment), both plain text
  whose lines may start with `[m:ss] ` / `[h:mm:ss] ` (the moment in the meeting; `parseKeyPointLines` /
  `parseTranscriptLines` in `src/lib/meeting-recorder/transcript-format.ts`; CRLF → `\n`, NUL dropped), `durationSec`
  (0–21,600), `createdBy`, `editedAt`/`editedBy`, and the recording: `audioType` (`MEETING_AUDIO_TYPES`: webm, mp4, ogg,
  wav, mpeg), `audioParts`, `audioBytes`, `audioExpiresAt`, `audioDeletedAt`. `MeetingRecapCategory` (0–5 per recap),
  `MeetingCategory` (one team-wide list, `nameKey` unique lower-cased, ≤ `MEETING_CATEGORIES_MAX` 30; the migration adds
  8 with fixed ids `meetingcat-<slug>`), `MeetingAudioPart` (stored file kind `meeting-audio`; `position` 0-based,
  unique per recap; the CHECK and the deletion trigger).
- **Saving** (`createMeetingRecap` → `{ id, audioRefused, duplicate, textKept }`): the text first, then the recording,
  so a failed upload never loses the text. The form declares the recording: `audioType` (normalised:
  `audio/webm;codecs=opus` → `audio/webm`), `audioBytes` (≤ `MEETING_AUDIO_MAX_BYTES`, 100 MB), `audioParts` (=
  `ceil(bytes / MEETING_AUDIO_PART_BYTES)`, 3 MiB parts). The whole size is checked against the storage cap first (no
  lock) — after purging recordings already past their 3 days (they'd still count until the purge runs; one quick
  `SELECT EXISTS` when none are due; best-effort: a failed purge — 5 s timeout — is only logged and they count this
  time, so it never stops a save or a part): if it won't fit, the recap is saved **without** the recording and
  `audioRefused` says why (it starts with `storageFullSentence`). `audioExpiresAt = ctx.now + MEETING_AUDIO_KEEP_MS`
  (72 h). A category deleted meanwhile → `MEETING_CATEGORY_GONE` on `categoryIds`. 20 new recaps per person per hour
  (`MEETING_RECAP_RATE_LIMIT`, counted after the checks). **Saving again is safe**: the recorder and the write-up form
  send a `requestId` (`newMeetingRequestId`: `crypto.randomUUID()`, or a v4 UUID from `getRandomValues` on a page
  that isn't a secure context; `parseMeetingRequestId` — anything else is ignored) that becomes the recap's id, so
  the same save again — after a lost answer, from the copy after a reload, or twice at once (the unique violation) —
  returns the first recap (`duplicate: true`), never counted toward the rate limit. Its text: while the recap is
  still that first save (the same person's, `editedAt` null and `updatedAt` still its `createdAt`), the retry is that
  save — its fields are checked as for a new one (a field error, nothing changed) and, when they differ, replace the
  first try's in one transaction conditional on the `updatedAt` read (`editedAt`/`editedBy` stay null; the version
  moves, so an open edit form hears of it; an edit landing first wins). Otherwise — edited since (or already changed
  by an earlier retry), or another admin's save — it keeps its text, and `textKept: true` says the retry's differed
  (fields that can't be saved count as different, never as a refusal); the forms then open the recap with
  `?saved=first`. Any admin may finish someone else's save (a shared browser's recorder copy: they can edit and
  delete it anyway). A retry keeping a recording the first save didn't get says `audioRefused` again
  (`MEETING_AUDIO_SAVED_WITHOUT`, or the storage reason), and a retry without one drops a declared recording none of
  which arrived (raw SQL; updatedAt stays). A recap deleted meanwhile is saved again. No schema change: it's just the
  id. `createMeetingRecapAction` never redirects and never echoes the form (a transcript can be 300,000 characters);
  it returns `recapId`, `audioRefused`, `duplicate`, and `textKept`, and drains the R2 objects of recordings it purged
  (`scheduleFileCleanup()`).
- **Editing** (`updateMeetingRecap` → `{ id, changed }`): `version` (updatedAt) checked before the fields
  (`MEETING_RECAP_CHANGED`); the same fields minus the recording; categories replaced in the same transaction;
  `editedAt`/`editedBy` only when the title, date, categories, key points, or transcript change (the length alone
  doesn't); a save that changes nothing writes nothing. The action redirects to `/meetings/<id>?saved=1` (`?saved=0`
  when unchanged); after a conflict it refreshes the page and echoes the values. The form (`MeetingRecapForm`) keeps
  the version it loaded until the admin chooses: a newer one only shows a warning ("Someone else saved this recap
  while you were editing") with **Save mine anyway** (saves over that version) and **Use their version** (after a
  confirm); Save changes alone moves focus to that warning. A new recap's form sends a `requestId` (made on the first
  Save, reused by later ones), like the recorder, so pressing Save again after a lost answer opens the recap it made
  (with the form's text, or `?saved=first` when it kept its own). `deleteMeetingRecap` (optional `version`) →
  `/meetings?removed=1` (also when it was already gone); the parts cascade and the action calls `scheduleFileCleanup()`.
  Edits and deletes share 120 per person per hour.
- **Uploading the recording** (`addMeetingAudioPart` → `{ complete, duplicate }`, one Server Action call per part:
  `uploadMeetingAudioPartAction`, fields `recapId`, `position`, `file`): every part but the last is exactly 3 MiB, the
  last what's left of the declared size; part 0 must sniff as the declared type (`sniffMeetingAudioType`: WebM
  `1A 45 DF A3`, MP4 `ftyp`, `OggS`, `RIFF…WAVE`, `ID3` / an MPEG audio frame); a position that's already there is a
  success (`duplicate`: a retry after a lost answer, nothing uploaded); past its 3 days or deleted → ConflictError. The
  row is created under the storage lock (`assertFileStorageRoom` per part; `precheck` before R2) with the recap's row
  locked (`FOR UPDATE`; expiry and duplicates re-checked: two uploads of one part at once make one row, and in R2 the
  loser's object is due for deletion); recordings past their 3 days are purged first, as when saving. It **never
  writes the recap's row** (an open edit form never goes stale). Complete = as many parts as declared and their sizes
  add up; the action refreshes the pages only then (and drains purged recordings' R2 objects). 300 parts per person
  per hour. `getMeetingAudioUploadState` lists the positions in, so the recorder can finish an interrupted upload from
  its IndexedDB copy; `getMeetingAudioUploadStateAction` answers `{ ok: true, state }`, `{ ok: false, gone: true }`
  only when the recap was deleted, or `{ ok: false, gone: false, message }` for anything else (signed out, no access,
  the database) — the recorder never treats those as "deleted" (`MeetingAudioUploadStateResult`).
- **The recording's state** (`meetingAudioState(recap, parts, now)` in every query; `MeetingAudioState`): `none`;
  `deleted` (`audioDeletedAt` set or `audioExpiresAt <= now`; `early` when deleted before its 3 days were up);
  `uploading` (`received` of `total`); `ready` (`partIds` in order, `audioType`, `audioBytes`, `expiresAt`).
- **Listening**: `GET /meetings/audio/[id]` (`getMeetingAudioPartFile` → `sendStoredFile` with `meetingAudioHeaders`:
  always an `application/octet-stream` download, `no-store`, nosniff, the sandbox CSP, same-origin) for any ACTIVE
  person while `audioDeletedAt` is null and `audioExpiresAt > now` — otherwise a 404, even before the purge got to it.
  Each response is ≤ 3 MiB (Vercel's limit; no Range support needed): the player fetches the parts in order, joins them
  into a Blob, and plays that.
- **3 days**: access ends exactly at `audioExpiresAt`, in every read. The bytes go with `purgeExpiredMeetingAudio(db,
  now, { limit, timeoutMs })` — a system job (no actor; a 30 s transaction by default, 5 s before a storage check),
  `FOR UPDATE SKIP LOCKED`, deletes the parts (the trigger queues their R2
  objects) and sets `audioDeletedAt` with **raw SQL** (updatedAt stays); unfinished uploads go the same way; running it
  again finds nothing. It runs (1) after the response on the meeting pages and in every meeting action
  (`scheduleMeetingAudioPurge`, `src/server/meetings/purge.ts`: one cheap `SELECT EXISTS` when nothing is due, then the
  purge and the R2 drain; never throws) and (2) once a day from **Vercel Cron** (`vercel.json`, `0 11 * * *` →
  `GET /api/cron/meeting-audio`, `maxDuration` 60, then `drainFileDeletions` for up to 40 s). With `CRON_SECRET` set
  (`env.cronSecret`) only `Authorization: Bearer <secret>` runs it (compared in constant time; else 401); without it,
  anyone may, at most 12 times an hour (429) — harmless, since it only deletes what's past its 3 days. The proxy lets
  exactly that path through without a session (compared as sent). (3) Right before a new recording (or part) is
  checked against the storage cap, so space every read treats as freed is free. (4) Optionally an R2 lifecycle rule
  on the `meeting-audio/` prefix (README). **Delete recording now** (`deleteMeetingAudio`): the parts go, `audioDeletedAt` is
  set with raw SQL, and the action calls `scheduleFileCleanup()`; already gone → `MEETING_AUDIO_ALREADY_DELETED`.

### Recorder (browser)

A port of VoiceCollector's recorder. **Privacy**: the audio and its transcription stay on the computer that recorded
it — speech recognition and the key points' first draft run in the browser (no API keys, no speech service); the
portal gets the saved text and, if the admin keeps it, the recording for its 3 days. Models and the wasm runtime are
only downloaded (from Hugging Face and jsDelivr) and kept by the browser.

- **Page**: `src/app/(meeting-recorder)/meetings/record/page.tsx` — its own route group (no AppShell, nothing to click
  away by accident), `force-dynamic`, admins only (`getMeetingRecorderSetup` → null sends everyone else to
  `/meetings`), entered with `RecorderLink` (a plain `<a>`, a clean page load). `MeetingRecorderApp`
  (`src/components/meetings/recorder/meeting-recorder-app.tsx`) runs the steps: **setup** (`recorder-setup.tsx`: this
  browser's unsaved copies — `recovery-list.tsx` — the microphone, the **Live transcript** switch — off by default on a
  phone or tablet without WebGPU — the model line with **Download it now** and **Smaller download**, Chrome's
  on-device summary with a one-time **Turn on**, "Let everyone know the meeting is being recorded.", **Start
  recording**, **Upload a recording**, Write one up) → **recording** (`recording-panel.tsx`: timer, level, Pause /
  Resume, **Mark key moment**, **Stop and review**, the live transcript with its first-text countdown and "no text
  after 90 s — the audio is safe") → **processing** (`processing-panel.tsx`: the live transcript's last window; no
  transcript, or only part of one → **Transcribe the recording now** or skip; drafting the key points) → **review**
  (`review-panel.tsx`: listen back, **Keep the recording for 3 days**, `MeetingRecapFields` controlled, **Save
  recap** / **Discard**) → upload → `/meetings/<id>?saved=new` (`?saved=first` when `textKept`; the review panel says
  so too while it stays open). A picked file goes straight to transcription. Words
  and pure decisions (default title "Meeting — Tue, Oct 7", progress lines, which files can be kept,
  `draftKeyPoints` / `suggestKeyPoints`, what an upload's end means for the copy, the leave guard's words):
  `src/lib/meeting-recorder/recorder-ui.ts`. While something isn't saved (recording, review, an upload running, or a
  saved recap's recording that's only in this tab — memory-only storage, or refused by the portal),
  `useLeaveGuard` asks before the tab closes and before any link leaves the page (`recorderLeaveMessage`). Leaving
  stops an upload (an `AbortController` the unmount aborts; the part in flight still lands) and nothing navigates
  afterwards (`openRecap` does nothing once unmounted); the copy finishes it later. **Accessibility**: status lines
  announce steps and decisions ("Downloading the speech model…", "Transcribing…", "There's no transcript yet.") —
  never a countdown's seconds or a download's percent, which are shown beside them (and in the progress bars); the
  processing step's line stays mounted through every step and takes focus when the button just clicked is gone.
- **Engine** (`src/components/meetings/recorder/engine/`, browser-only TypeScript, no React; each file's header documents
  its API): `mic.ts` (the raw microphone — no echo cancellation or noise suppression, automatic gain — and a
  24 kbps Opus `MediaRecorder` with a 5 s timeslice), `pcm-tap.ts` + `public/asr/v1/pcm-tap-worklet.js` (a 16 kHz tap
  in an AudioWorklet), `asr-client.ts` ↔ `public/asr/v1/asr-worker.js` (the model in a module Web Worker — building it
  can block a thread for minutes; messages `probe`, `load {model, device, ortVariant}` → `status` events → `load:ok`,
  `transcribe {pcm (transferred), timestamps}` → raw `{text, chunks}`, `dispose`; every call has a timeout and a stuck
  worker is killed), `live-session.ts` (`MeetingRecorder`: MediaRecorder + tap + windower + model + the IndexedDB
  copy, pause left out of every timestamp, marks, wake lock, auto-stop at 3 h, a lost microphone stops it and keeps
  what was recorded; `transcribeBlob` for whole files), `decode.ts` (to 16 kHz; 200 MB / 3 h), `fix-duration.ts`,
  `wake-lock.ts`, `recorder-db.ts`, `chrome-summarizer.ts`, `upload.ts`. Text handling is pure and unit-tested in
  `src/lib/meeting-recorder/*` (`stream-windower.ts`: 25 s windows with 3 s overlap, audio buffered from the first
  second until the model is ready (up to 240 s), quiet windows skipped (`vad.ts`), a jump forward when inference falls
  behind; `transcript-text.ts`: overlap joining, loop and repeat filters, Whisper's silence phrases dropped on quiet
  audio).
- **Models** (`ASR_MODELS`; pinned revisions, Hugging Face at run time, kept in Cache Storage `huskyteers-asr`):
  WebGPU with `shader-f16` → `whisper-small.en` q4/q4 (~286 MB); otherwise, after a WebGPU failure (timed from the end
  of the download), or with **Smaller download** → `whisper-base.en` q8/q8 on the CPU (~73 MB) in a fresh worker.
  Never q8 on WebGPU (it hangs), never `language`/`task` for `.en` models, `env.allowLocalModels = false` (the portal
  would answer `/models/…` with its sign-in page). onnxruntime-web's wasm from jsDelivr at the version transformers.js
  4.3.0 pins (`.asyncify`; plain only for Safari < 26 without WebGPU, decided on the page). No COOP/COEP: single-thread
  wasm is enough. `public/asr/v1/` is cached for good (`immutable`): change any file there → copy the folder to `v2`.
- **This browser's copy** (`recorder-db.ts`, IndexedDB `huskyteers-recorder` v1: `recordings` docs, `chunks`
  `<id>#<seq6>`): every 5 s chunk as it comes; the doc 3 s after a change, every 10 s, and at once on pause, mark, and
  stop; the review form 1 s after typing; a picked file as chunk 0 (when it can be kept). Status `recording` →
  `stopped` → `uploading` (with `recapId`) → deleted only once the portal has the whole recording (or the recap was
  saved without it), or when the admin discards it — never because a check failed (`copyAfterUpload`): a deleted recap
  (only `gone`) turns the copy back into an unsaved recording (no `recapId`, a new request id) to save as a new
  recap; past its 3 days it stays until discarded. Each save's `requestId` is written into the copy before it's sent,
  so saving again after a reload finds the same recap; a `textKept` answer is written in too (finishing the upload
  then opens `?saved=first`), and a copy whose recap kept its own text isn't deleted while the recorder was left —
  only once that can be said. Discard stops a due review autosave from writing the copy back.
  Discarding an interrupted upload's copy (the list, or **Finish uploading**) first deletes what reached the portal
  (`deleteMeetingAudioAction`, only while it's still uploading there — `serverAudioToDelete`), so the recap says "The
  recording was deleted" instead of "still uploading" for 3 days; if that fails, nothing is deleted and the message
  says so. Blocked IndexedDB (or a failed write) → memory only, with a warning to keep the tab open (and a failed
  upload offers **Download the recording**, `uploadFailedHint`). Audio over 3 days old is
  deleted when the page loads (the text stays). A tab holds a Web Lock (`huskyteers-recorder:<id>`) on the recording
  it has open, so other tabs don't offer it; a `recording` nobody holds was cut off and is offered right away
  ("Unsaved recording from … · 47:12 · 312 lines": **Review & save** / **Discard**; without Web Locks, after 15 s
  without a heartbeat).
- **Saving**: `createMeetingRecapAction` with the declared recording (or none), then `uploadRecording` — 3 MiB parts,
  one `uploadMeetingAudioPartAction` each, in order, 3 retries with growing pauses on network errors, stopped by a
  refusal ("Uploading the recording… 3 of 5 (9 MB of 14 MB)"). `audioRefused` → saved without it (download offered).
  An upload that stopped: **Try the upload again** now, or **Finish uploading** later from the setup screen
  (`getMeetingAudioUploadStateAction` → `resumeUpload`: the parts in are skipped; only a deleted recap is "orphaned" —
  saved again as a new one; a check that couldn't be made is just a failure to try again; past its 3 days, nothing to
  finish). A save answered `duplicate` resumes the upload the same way.
- **Key points** (`draftKeyPoints`): the extractive ranker in `key-points.ts` (decisions, to-dos with the owner from
  the roster of first names and the deadline, emphasis, marked moments, then the most content-rich sentences, spread
  over the meeting) merged with Chrome's `Summarizer` (`type: "key-points"`) when it's ready — created in the Start
  click (its download needs the click; the setup's **Turn on** does it once), fed the transcript after Stop, every call
  with a timeout, garbage refused. One `[m:ss] ` line each, edited before saving.
- **Edit page tools** (`src/components/meetings/recap-edit-tools.tsx`, in `MeetingRecapForm`'s
  `keyPointsActions` / `transcriptActions`): **Suggest key points** (from the transcript box; empty key points are
  filled, otherwise **Replace the key points** / **Add them below**) and, while the recording is kept, **Transcribe
  the recording again** (the parts → `transcribeBlob` → **Replace the transcript**). Nothing changes until the admin
  picks, and nothing is saved until **Save changes**.
- **Tests**: `tests/meeting-recorder-*.test.ts` (formats, transcript text and VAD, the windower with a fake model, key
  points on a realistic FTC meeting, the part upload, the worker client with a fake Worker, the recorder page's

  `recorderLeaveMessage`); `e2e/meeting-recorder.spec.ts` (desktop, Chrome's fake microphone: live transcript off,
  pause, a key moment, Stop → skip → review → save → `MeetingAudioPart` rows → the recap plays; a recording cut off by
  leaving is offered again and discarded, with the autosave due; leaving mid-upload never navigates afterwards; a
  discarded interrupted upload deletes what reached the portal; with `E2E_WHISPER=1`,

## Discussion (`src/server/services/discussion.ts`, `/discussion`)

The team-wide forum (Questions stay private member → leader threads). Everyone ACTIVE reads every discussion, starts
one (`DiscussionThread`: title, text shown with `RichText`, `category` from `DISCUSSION_CATEGORIES`), and replies
(`DiscussionReply`). No emails. Pages: `/discussion` (list), `/discussion/new` (`?category=` preselects), `/discussion/[id]`,
`/discussion/[id]/edit`; client-safe helpers (URL filters, links, the divider rule) in `src/lib/discussion.ts`.

- **Who**: only whoever wrote a post changes its text (`canEditDiscussionPost`, never moderators). A discussion is
  deleted by its author while nobody else replied (checked with the row locked; a reply from a deleted account counts
  as someone else's) and by everyone with admin access any time (`canModerateDiscussion` = `canAdminister`), who also
  **pin** (listed first) and **lock** it. A reply is deleted by its author or a moderator. **Locked** = frozen: no new
  replies and no edits from anyone (a moderator who wants a last word unlocks, replies, and locks again), and only
  moderators delete in it (authors can't take a post back, e.g. a vote; `DISCUSSION_LOCKED_DELETE`, checked with the
  row locked). Accounts that aren't ACTIVE get `ForbiddenError` on every write and `null`/0 from the queries. Accounts
  with posts can't be deleted (`NO_ACTIVITY` in `services/admin.ts`), so posts keep their author.
- **Counts**: `replyCount` and `lastActivityAt/By` (the list's order and "last reply 2 h ago by Ethan") change in the same
  transaction as the reply, with the discussion's row locked first (`createReply`: one raw `UPDATE … WHERE NOT locked
  RETURNING`, which also picks the reply's time under that lock: now, but always after the last activity, so replies
  are timed in the order they're saved and a slow request can't land behind someone's read mark). `deleteReply` locks
  the row, deletes, and **recounts** both from what's left (the newest reply, else the discussion itself), so they're
  right after deletes and races.
- **Versions**: the edit form (`/discussion/[id]/edit`) and a reply's inline edit send `version` (the `updatedAt` they
  loaded): a stale save is a `ConflictError`, checked before the fields; the actions refresh after it, so saving again
  replaces it. They don't refresh when the post is gone (or, on the edit page, was just locked): the form stays with
  the typed text and says why, instead of turning into a 404 or losing the reply. `/discussion/[id]/edit` sends
  anyone who can't edit it (not theirs, or locked) to the discussion; a 404 only when it's gone. Only text edits move
  `updatedAt` (always to a new value, `nextVersion`): replies, pins, and locks write with raw SQL, so they never make
  an author's edit a conflict. Edits set `editedAt` ("edited"; not activity: the list order and unread marks don't
  move); saving unchanged writes nothing.
- **Unread**: `DiscussionRead(userId, threadId, lastReadAt)`. A discussion is unread for me when its `lastActivityAt` is
  after my mark — or, never opened, after my account's `createdAt` — and the last activity wasn't mine (a deleted
  account's counts as someone else's). `countUnreadDiscussions` (nav badge) is one raw count; the list's **Unread**
  filter and markers ("New" = started by someone else after I joined and never opened; "3 new" = replies since my mark)
  use the same SQL (`UNREAD` in `queries/discussion.ts`). The page marks it read with `<ThreadReadState>`: a Server
  Action **after mount** and once the tab is visible (`markThreadReadAction`, never on render, so prefetching or a
  background tab can't mark anything), up to the newest activity the page shows (`seen` = the newest reply it loaded,
  else the discussion; not `lastActivityAt`, which is read separately; capped at now; marks never move back), again
  only if a refresh shows newer activity. The action refreshes the page only when the mark moved (`{ moved }`).
  Replying also marks it read. The **New** divider goes before the first reply by someone else since my
  mark (`firstNewReplyId`; never opened: since I joined, or nothing when the whole discussion is new to me) and keeps
  its place while the page is open (client state), so the refresh after marking doesn't take it away; so does the
  "Jump to new replies" link under the title (`JumpToNewReplies`: scrolls to it and moves focus there).
- **List** (`listDiscussionThreads`, raw SQL): pinned first, then `lastActivityAt` desc, 30 a page; `?category=`,
  `?unread=1`, `?mine=1`, `?q=` (title, `cleanSearchText` + `escapeLike` with `ILIKE`), all validated
  (`parseDiscussionFilters`). The active category chip is scrolled into view (`KeepChipInView`) and the count names it
  ("3 discussions in Ideas"); a card's link name includes what's new ("… (2 new replies)"). **Page**: the newest
  `DISCUSSION_REPLIES_SHOWN_MAX` (500) replies, oldest first, with a note when older ones are left out (counts come
  from the replies loaded, so a reply saved mid-load can't fake one); each shows name + position (`describeRole`),
  time, "edited". Posting a reply
  redirects to `?posted=<id>#reply-<id>`: that reply (only one of mine on the page) takes focus and says "Reply posted.",
  and the reply box remounts empty. Inline reply edits keep the text in state, move focus into the box and back, and
  announce "Reply updated." in the reply's status line. Deleting goes to `?deleted=1` / `/discussion?removed=1`.
- **Limits**: `LIMITS.discussionTitleMax` / `discussionBodyMax` / `discussionReplyMax`; `DISCUSSION_RATE_LIMITS`: 10 new
  discussions, 60 replies, and 120 saved edits (discussions and replies together) per person per hour (counted after
  the form is valid; an unchanged save isn't counted).
- **Demo**: the seed adds four with fixed ids (`demo-thread-welcome` pinned, `demo-thread-shirts` locked,
  `demo-thread-autos`, `demo-thread-intake`) and read marks, so some people start with unread ones; e2e and the tour
  open them by id.

## Public progress (team website)

The team website (`https://huskyteers19516.github.io/progress`, its own repo, a static Astro site on GitHub Pages)
shows guests the team's live progress by polling **`GET /api/public/progress`** every 30 s
(`src/app/api/public/progress/route.ts` → `publicProgressResponse` in `src/server/public-api.ts` →
`getPublicProgress` in `src/server/queries/public-progress.ts`; types and client-safe helpers in
`src/lib/public-progress.ts`). Which paths answer without a session, the CORS and caching rules, and the Sponsors and
Events endpoints next to it are in **Public API for the team website** below. The route never reads cookies, so it can
be cached publicly. Never add anything personal to it.

- **Answer**: `{ enabled: true, team: { name, number }, since, updatedAt, totals: { itemsDone, itemsOpen,
  itemsSubmitted, completion, doneLast7Days, tasksFinished, tasksActive, people }, subteams: [{ key, name, itemsDone,
  itemsOpen, itemsSubmitted, completion, doneLast7Days, tasksActive, people }] (always SOFTWARE, BUILD, BUSINESS),
  people: [{ id, name, subteam, role, itemsDone, itemsOpen, itemsSubmitted, completion, doneLast7Days, lastDoneAt }],
  recent: [{ title, subteam, who, at }], weekly: [{ weekStart, itemsDone }] }`, or just `{ enabled: false }` while it's
  turned off.
- **Who counts**: ACTIVE accounts that aren't mentors or teachers (`publicStudentsWhere`: members, subteam leaders, the
  captain; owners by their position). Pending, turned-down, and disabled accounts never appear anywhere in it.
  `User.hideFromPublicProgress` ("Show me on the team website's progress page" off, in Settings —
  `updatePublicProgressVisibility`, your own account only) takes a person off `people` and out of `recent` entirely
  (a title and a time could still point at them). Their items count in `totals`, `subteams`, `weekly`, the task
  counts, and the `people` counts only when at least `PUBLIC_HIDDEN_MIN_GROUP` (2) people in the same group — a
  subteam, or everyone without one (the captain) — are hidden; below that they're left out of every number
  (`uncountedHiddenIds`), since the group's total minus its listed people would be exactly theirs. Admin → Team website
  says how many are hidden and how many of them aren't counted. Mentors and teachers get no switch (never listed).
- **What counts**: the checklist items (`TaskAssignment`) of tasks whose **due date is on or after `since`** (future
  due dates included). `itemsDone` = APPROVED (including "counted with the whole task", `finishedWithTask`);
  `itemsOpen` = TODO / SUBMITTED / REJECTED on tasks **not** marked finished; closed items (not approved on a finished
  task) count as neither. `itemsSubmitted` = the SUBMITTED part of `itemsOpen` (checked off, waiting for review — the
  page shows it as its own segment). `completion` = `round(100 × done / (done + open))`, 0 when both are 0 (the page
  shows "—").
  "Done when" = `reviewedAt` (the finish time for whole-task credit): `doneLast7Days` = approved on today or the 6 days
  before (team timezone), `lastDoneAt` = the newest, `weekly` = approvals per Monday–Sunday week (team timezone,
  `AT TIME ZONE` in SQL, so daylight saving is right), zero-filled, the current week last: the last 8 weeks, but
  starting at the week `since` falls in when that's later (no empty weeks from before the season), and at least the
  current week (`firstPublicWeek`). Times (`lastDoneAt`, `recent[].at`) are to the minute (`publicTime`).
  Subteams go by the **person's** subteam (the captain counts in `totals` only); a subteam's `tasksActive` = tasks
  with an open item of someone in it. Team `tasksActive` = tasks with an open counted item; `tasksFinished` = the other
  tasks with counted items (marked finished, or every counted item approved). Tasks with no counted items (only a
  mentor on it, nobody) aren't counted.
- **`recent`**: the newest `PUBLIC_RECENT_MAX` (15) approvals, newest first, without whole-task credit (one finished
  task could fill it — the same rule as the overview's Recent activity) and without anyone who hid themselves.
  `title` = the task's title (null when task titles are off — titles are free text and go to the open internet, the
  Admin card says so), `subteam` = the person's, `who` = their name as the page shows names (null when names are
  hidden).
- **Names and positions**: `nameStyle` `full` ("Ethan Chen", the default — the team page already lists full names),
  `first-initial` ("Ethan C."), `initials` ("E.C."), or `hidden` (`people: []`, every `who` null) — `publicName`.
  Positions in the team website's words (`publicRoleLabel`): Captain, Software/Build/Business Lead, Software/Build/
  Business Team. `people` is sorted by subteam (Software, Build, Business, then none) and name — not ranked.
- **Ids**: `id` = HMAC-SHA256(salt, `person:<name style>:<account id>`), base64url, 16 characters
  (`publicPersonId`): stable between polls, never the account id, and new whenever the name style changes (a copy saved
  with full names can't be matched up by id with later initials). The salt is 32 random bytes in the TeamNote
  `public-progress-id-salt` (`publicProgressIdSalt`), made when the settings are saved, so the anonymous request
  normally only reads; if it's still missing, the first request that needs ids makes it (`createMany …
  skipDuplicates`, then read back, so two first requests agree; one that's too short is replaced). With names hidden
  it isn't touched. Changing it gives everyone new ids.
- **Never in it**: emails, submission or review notes, due dates or overdue/late info, questions, task or account ids,
  anything about mentors, teachers, or accounts that aren't ACTIVE. `tests/public-progress.test.ts` checks each.
- **One person** (**`GET /api/public/progress/people/<id>`**, the website's Our Team page opens it from a person's
  card; `src/app/api/public/progress/people/[id]/route.ts` → `publicPersonProgressResponse` →
  `getPublicPersonProgress`; types `PublicPersonProgress` / `PublicPersonDone` in `src/lib/public-progress.ts`).
  `<id>` is a `people[].id` from the progress JSON. Answer: `{ enabled: true, updatedAt, since, person, weekly, done }`
  — `person` is **exactly** their `people` entry (same fields, order, and numbers: the same SQL pieces —
  `countedItemsSql`, `personCountsSql`, `weeklySql`, `publicPersonEntry` — filtered to them), `weekly` their approvals
  over **the same weeks** as the progress JSON's `weekly`, and `done: [{ title, subteam, at, withTask }]` — their newest
  `PUBLIC_PERSON_DONE_MAX` (25) approvals (APPROVED with a `reviewedAt`, tasks due on or after `since`), newest first:
  `title` the task's (null while task titles are off), `subteam` **the task's** (null for a team-wide task; theirs is
  `person.subteam`), `at` to the minute, `withTask` = counted when a leader marked the whole task finished
  (`finishedWithTask`; unlike `recent`, whole-task credit is listed here, marked — it's one person's own list).
  **Otherwise one JSON 404** `{ error: PUBLIC_PERSON_NOT_FOUND }` (`no-store`, the usual CORS headers), byte-for-byte
  the same whatever the reason: the page off, the profiles off (`showPersonPages`, the default), `nameStyle` "hidden"
  (the progress JSON lists nobody), no salt yet (no id
  can have been handed out — this endpoint never makes it), an id that isn't 16 base64url characters
  (`PUBLIC_PERSON_ID_RE`; answered without touching the database or the cache), or an id that isn't a **listed**
  person's — unknown, someone who turned off "Show me on the team website", a mentor or teacher, an account that isn't
  ACTIVE. Those last ones are one code path (the id is looked for only among the listed people, an HMAC each), so
  nothing tells them apart; an id made for another name style is unknown too. Never emails, notes, review notes, due
  dates, overdue/late info, or account or task ids (`tests/public-progress.test.ts`). **Cost**: never a write; the
  database work never depends on what's in the address. The route keeps a **directory** of who can be found
  (`getPublicPeopleDirectory`: settings, then the listed people with their public ids — two reads; null while anything
  above is off) for `PUBLIC_ANSWER_TTL_MS` (`cachedPublicValue` with the route's `createPublicValueCache()`). An id that
  isn't in it — made up, hidden, any of the reasons above — is the 404 straight from memory: no read, no cache entry.
  Only a listed id builds (`getPublicPersonProgressFor`: their counts, weeks, and approvals — three reads) and is kept
  **per id** for `PUBLIC_ANSWER_TTL_MS` (`cachedPublicAnswerByKey` with the route's
  `createPublicAnswerCacheMap(PUBLIC_PERSON_CACHE_MAX)`, 100 ids, least recently asked dropped first — only listed
  people reach it, so a flood of made-up ids can't push them out). `getPublicPersonProgress(db, { now, teamTimezone,
  id })` is both in one (at most five reads). Someone who hides themselves disappears within the same ~10 s (plus the
  CDN's 15 s) as from the progress JSON.
- **Settings** (TeamNote `public-progress`, JSON, `parsePublicProgressSettings` falls back to the defaults field by
  field): `enabled` (true), `nameStyle` ("full"), `showTaskTitles` (true), `since` (null = the attendance schedule's
  `reportStart`, default 2026-08-31; the Events page starts there too), `showSponsors` (**false**) and `showEvents`
  (**false**) — the Sponsors and Events pages' own switches, independent of `enabled`, **off until someone with admin
  access turns them on** (settings saved before they existed read as off), so sponsors and events already in the
  portal — imported from a spreadsheet, written for the team — never go public on their own. Under each switch the card
  says what it shows, or would show once on (`getTeamWebsitePreview` in `queries/team-website.ts`: how many sponsor
  entries, how many without a logo, how many events — counts only). `showPersonPages` (**false**): each listed
  person's profile on the website's Our Team page (the person endpoint below; it also needs `enabled` and names shown)
  — **off until someone with admin access turns it on**, so nobody's task-by-task history goes public on its own; the
  card's box says exactly what a profile lists, the task titles box covers Recent completions and the profiles, and
  each member's own switch (Settings → Team website) says what their profile shows and whether profiles are on. The
  demo seed turns sponsors, events, and profiles on. `showPhotos` (**true**): members' own photos on the Our Team page
  (`GET /api/public/team-photos`, below) — on, because each person already chose for their own photo (on by default,
  with a switch that says the site is public); off answers `{ enabled: false }` and serves no photo (a missing value
  reads as on; the card says how many photos show, `TeamWebsitePreview.photos`). Changed in **Admin → Approvals → Team website** (`TeamWebsiteCard`, everyone with admin access —
  `canManagePublicProgress`; `updatePublicProgressSettings`: unchecked boxes = off, an empty date = null, a date within
  5 years back / 1 year ahead, `PUBLIC_PROGRESS_SETTINGS_RATE_LIMIT` 60 saves an hour), which also links to the pages
  and the JSON and says how many people hid themselves (a count only). The card's On/Off badge is the progress switch.
- **HTTP**: `publicProgressResponse` is a thin wrapper around `publicJsonResponse` (see **Public API for the team
  website**: GET / HEAD / OPTIONS, CORS for the team website only, `public, s-maxage=15, stale-while-revalidate=45`, a
  503 `{ error }` with `no-store`), so a settings change shows within about a minute.
- **Cost**: one settings read, then five queries **one after another** (people, per-person counts, tasks per subteam
  with `GROUPING SETS`, weekly buckets, recent), so a build holds one pool connection at a time — the counts are SQL
  aggregates with enum values as literals, never one query per person. The built JSON is kept in memory for
  `PUBLIC_ANSWER_TTL_MS` (10 s) per server instance (`cachedPublicAnswer`), so the database work doesn't depend on the
  query string.

## Public API for the team website

The team website (its own repo, static Astro on GitHub Pages; its `PUBLIC_PORTAL_URL` points here) reads public JSON
and images from `src/app/api/public/**` in the browser, without signing in: `/progress` and `/progress/people/<id>`
(above), `/sponsors`, `/events`, `/workshop` (see **Workshop (team website)**), `/team-photos` (members' photos,
below), and `/site-content` with `/site-images/<id>` (see **Website Coding**). Another feature adding a public endpoint follows exactly this.

- **Which paths are public** (`src/lib/public-api.ts`, client-safe): `PUBLIC_API_PATHS: readonly string[]` (exact
  paths: `PUBLIC_PROGRESS_PATH`, `PUBLIC_SPONSORS_PATH`, `PUBLIC_EVENTS_PATH`, `PUBLIC_WORKSHOP_PATH`,
  `PUBLIC_TEAM_PHOTOS_PATH`, `PUBLIC_SITE_CONTENT_PATH`; `src/lib/public-progress.ts` re-exports
  `PUBLIC_API_PATHS` and `PUBLIC_PROGRESS_PATH` so older imports keep working), `PUBLIC_API_FILE_PREFIXES: readonly
  string[]` — the **id routes** (the name is older than the one JSON id route; it means "prefix + one id"), each
  ending with "/": `PUBLIC_SPONSOR_LOGOS_PREFIX` = `/api/public/sponsors/logos/`,
  `PUBLIC_WORKSHOP_PHOTOS_PREFIX` = `/api/public/workshop/photos/`, `PUBLIC_WORKSHOP_FILES_PREFIX` =
  `/api/public/workshop/files/`, `PUBLIC_PROGRESS_PEOPLE_PREFIX` = `/api/public/progress/people/` (JSON),
  `PUBLIC_TEAM_PHOTOS_PREFIX` = `/api/public/team-photos/`, `PUBLIC_SITE_IMAGES_PREFIX` = `/api/public/site-images/`,
  `PUBLIC_API_ID_RE = /^[A-Za-z0-9_-]{1,64}$/`, and `isPublicApiPath(pathname): boolean` — true for an exact
  `PUBLIC_API_PATHS` entry, or a prefix followed by exactly one segment matching `PUBLIC_API_ID_RE` (so no further "/",
  no "%" escapes such as `%2f` or `%2e`, no dots, nothing empty or longer than 64). The proxy (`src/proxy.ts`) uses it
  on the path as sent (never decoded); anything else under `/api/public/` still gets the JSON 401 without a cookie.
  `tests/public-progress.test.ts` walks `src/app/api/public`: a static route must be in `PUBLIC_API_PATHS`, an `[id]`
  route only when its parent path + "/" is in `PUBLIC_API_FILE_PREFIXES` (and every listed path / prefix has its
  route); each route must import `@/server/public-api` and never read the session, cookies, or headers.
- **JSON** (`src/server/public-api.ts`): `publicJsonResponse(request, { extraOrigins, now, cache?, build,
  unavailableMessage, logTag, extraHeaders? }): Promise<Response>` (`extraHeaders`: more headers on the 200 — members'
  photos send `PUBLIC_NO_INDEX_HEADERS`) — `build: () => Promise<string>` returns the answer's JSON text.
  GET / HEAD answer it (`Content-Type: application/json; charset=utf-8`), OPTIONS is the preflight (204,
  `Access-Control-Allow-Methods: GET, HEAD, OPTIONS`, `Max-Age` a day), anything else 405 with `Allow`.
  `Access-Control-Allow-Origin` = the request's `Origin` when it's `https://huskyteers19516.github.io`
  (`TEAM_SITE_ORIGIN`) or in `PUBLIC_PROGRESS_EXTRA_ORIGINS` (comma-separated, e.g. `http://localhost:4321` for working
  on the website; only http(s) origins, `*` is ignored), **otherwise the team website** — never another site, never `*`,
  never credentials (so a CDN copy that ignored `Vary` still works for the team website). Always `Vary: Origin`,
  `Cache-Control: public, s-maxage=15, stale-while-revalidate=45` (`PUBLIC_CACHE_CONTROL`: Vercel's CDN answers most
  requests), `X-Content-Type-Options: nosniff`. A failed build is logged as `[<logTag>] couldn't build the answer` and
  answered with a 503 `{ error: unavailableMessage }`, `no-store`. Optional `notFoundMessage` (only an endpoint with a
  "not here" answer — one person's progress): a build answering JSON `null` is a 404 `{ error: notFoundMessage }`,
  `no-store`, with the same CORS headers; without it every build is a 200, as before.
  `cachedPublicAnswer(cache: PublicAnswerCache | undefined, now: Date, build: () => Promise<string>): Promise<string>`
  keeps a build for `PUBLIC_ANSWER_TTL_MS` (10 s): the CDN keys copies by the whole URL, so `?anything=<random>` always
  reaches the server, and this makes the database work independent of the query string. One shared build per server
  instance at a time (each route keeps its own `createPublicAnswerCache()` at module level); a failed build isn't kept;
  no cache = build every time. An id route's JSON keeps one such answer **per id**:
  `createPublicAnswerCacheMap(max): PublicAnswerCacheMap` (at module level in the route; `max` ≥ 1 keys) and
  `cachedPublicAnswerByKey(map | undefined, key, now, build): Promise<string>` — `cachedPublicAnswer` for that key's
  entry, the key moved to most recently used, the least recently used dropped past `max` (so made-up ids can't grow
  it; a build in flight still answers its waiters); no map = build every time. Check the id's format before using it as
  a key, and keep only ids worth keeping (the person route looks the id up in a cached directory first). Any other
  built value (not JSON text) uses `createPublicValueCache<T>(): PublicValueCache<T>` and `cachedPublicValue(cache |
  undefined, now, build)` — the same rules (`cachedPublicAnswer` is it for strings). `publicProgressResponse` / `publicSponsorsResponse` / `publicEventsResponse` / `publicWorkshopResponse(request,
  { db, now, teamTimezone, extraOrigins?, cache? })` and `publicPersonProgressResponse(request, { db, now,
  teamTimezone, extraOrigins?, cache?: PublicAnswerCacheMap, directory?: PublicValueCache<PublicPeopleDirectory |
  null>, id })` are the thin wrappers the routes and tests call.
- **Files** (`publicFileHeaders({ contentType, filename, inline, immutable }): Headers`, the caller adds
  Content-Length): `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`
  (`PUBLIC_FILE_CSP`), `Content-Disposition` inline or attachment with a safe filename (`contentDisposition`: an ASCII
  fallback plus the UTF-8 name), `Cross-Origin-Resource-Policy: cross-origin` (the website embeds it; no CORS header is
  needed for an `<img>`), and public caching: `immutable` → `PUBLIC_FILE_IMMUTABLE_CACHE` (only when the address
  changes with the content; see below), else `public, max-age=60, s-maxage=60`. Only pictures (`PUBLIC_INLINE_TYPES`: PNG, JPEG, WebP, GIF) are ever inline, with
  their own type; anything else (SVG, HTML, PDF — Chrome won't show a sandboxed PDF) is an `application/octet-stream`
  attachment whatever `inline` says. `filename` is always a neutral public name (sponsor logos:
  `publicSponsorLogoFilename` → "rev-robotics-logo.png"; Workshop photos "workshop-photo.jpg"), never the name it was
  uploaded with (that can hold someone's name, a phone's or a folder's) — except Workshop design files, whose cleaned
  name is part of what a reviewer approves (see **Workshop (team website)**).
  A public file route is a thin wrapper around **`publicFileResponse(request, { id, load, filename, inline, immutable,
  notFoundMessage, logTag, store?, extraHeaders? })`** (`extraHeaders`: more headers on the file's answer — members'
  photos: `PUBLIC_NO_INDEX_HEADERS`), which: (1) answers an id that isn't `PUBLIC_API_ID_RE` with a plain 404;
  (2) answers **any query string** with a `308` to the bare address (relative `Location`, `PUBLIC_FILE_REDIRECT_CACHE`)
  **before touching the database or R2** — the CDN keys copies by the whole URL, so without this `?cb=1`, `?cb=2`, …
  would each read the whole file again (the team website never adds a query to a file address); (3) calls `load(id)`,
  which must read the row **only while its owner is public, in one query with the check in its WHERE** (null → plain
  `404`, `private, no-store` — never cached, so it can come back; a database failure → plain 503
  `PUBLIC_FILE_UNAVAILABLE`); (4) sends it with `sendStoredFile` (Postgres, or streamed from R2) and
  `publicFileHeaders`, turning R2's own errors into the plain 404 (missing object) or 503 `PUBLIC_FILE_UNAVAILABLE`
  (not set up / not answering) — never the signed-in pages' messages about R2's settings. HEAD sends the headers only.
  `immutable` caching is `public, max-age=86400, s-maxage=300, immutable`: browsers a day, Vercel's CDN 5 minutes (so a
  file taken off the website stops being served from the CDN within minutes, and the server reads each file about once
  per 5 minutes per CDN region).
- **Sponsors** (`GET /api/public/sponsors`, `getPublicSponsors` in `queries/public-sponsors.ts`, types in
  `src/lib/public-sponsors.ts`): `{ enabled: true, updatedAt, sponsors: [{ name, url, years, logo }] }`, or
  `{ enabled: false }` while `showSponsors` is off. Only public sponsors (ACCEPTED or FINISHED with `showOnWebsite`,
  `publicSponsorsWhere`; the newest `PUBLIC_SPONSORS_ROW_CAP` = 1000 rows). Grouped by the public name

  = every row's year, merged, ascending — a row's year is its `acceptedOn` year, else `submittedOn`'s, else the year it
  was added (`createdAt`, team timezone) (`sponsorPublicYear`); `name` = the newest row's spelling (by year, then when
  it was added) unless it's all lower-case and another row's has capitals (`pickPublicSponsorName`: a hasty
  "rev robotics" doesn't rename "REV Robotics"); `url` = the **homepage only** of the newest row's http(s) website
  (`publicSponsorUrl`: origin + "/", never a path, query, or #fragment — the Website field also holds application
  pages, whose address can carry ids or tokens), else null; `logo` =
  `/api/public/sponsors/logos/<SponsorshipLogo.id>` of the group's newest logo (relative: the website puts its
  `PUBLIC_PORTAL_URL` in front), or null. Sorted by latest year (newest first), then name (`Intl.Collator`). **Never**

  without their metadata (see **Sponsorships**).
- **Events** (`GET /api/public/events`, `getPublicEvents` in `queries/public-events.ts`, types in
  `src/lib/public-events.ts`): `{ enabled: true, updatedAt, timezone, events: [{ id, title, kind, kindLabel, startsOn,
  endsOn, startTime, endTime, location, link }] }`, or `{ enabled: false }` while `showEvents` is off. Only
  `PUBLIC_EVENT_KINDS` (MEET, ILT, SCRIMMAGE, COMPETITION, OUTREACH — never MEETING "Extra meeting", TEAM, DEADLINE,

  start), through the future; at most `PUBLIC_EVENTS_MAX` (300) — the latest by first day, so what's coming up is never
  cut — ordered by first day, start time (all day first), title. `id` = the calendar event's id; `kindLabel` the
  calendar's label ("League meet"); `endsOn` null for one day; times "HH:MM" in `timezone` (the team's, e.g.
  America/Los_Angeles), `endTime` only with a start time; `link` http(s) or null. **Never** notes, who added or edited
  it, or `sourceKey` — `tests/public-events.test.ts` checks each.
- **Members' photos** (`GET /api/public/team-photos`, `publicTeamPhotosResponse` → `getPublicTeamPhotos` in

## Workshop (team website) (`src/server/services/workshop.ts`, `/workshop`)

What the team designs and builds — `WorkshopProject.kind` PART ("3D prints & CAD", first on the website), SOFTWARE, or
OTHER ("Other builds") — with photos of each version (`WorkshopPhoto`) and design files anyone can download
(`WorkshopFile`). Approved projects are shown to guests on the team website's Workshop page
(`https://huskyteers19516.github.io/workshop`, deep link `#<project id>`). Client-safe labels, limits, checks, and the
public types: `src/lib/workshop.ts`.

- **Who**: everyone ACTIVE adds projects. Whoever added one, the people credited on it (`WorkshopCredit`, ACTIVE
  accounts when added — one who has left stays credited), and everyone with admin access (`canReviewWorkshop`, the
  reviewers) change it (`canEditWorkshopProject`): details, credits, photos, files. Removing a whole project: whoever
  added it and reviewers (`canDeleteWorkshopProject`; credited people can take their own name off). Approved projects
  are seen by everyone ACTIVE; the rest only by the people who can change them and reviewers (`visibleWorkshopWhere`).
- **Status** (`WorkshopStatus`): a new project is a DRAFT. **Send for approval** (`submitWorkshopProject`, needs at
  least one photo: DRAFT / REJECTED → PENDING); reviewers **Approve** (→ APPROVED, `publishedAt` set the first time) or
  **Send back** with a required note (→ REJECTED, `reviewNote`) — `reviewWorkshopProject`, only while PENDING
  (row-locked). For a reviewer, Send is **Publish** (straight to APPROVED, on any project they can open — their own or
  someone's draft). Approve and Publish carry `version` (the
  project's `updatedAt` as the reviewer saw it): if it changed since — someone added a photo or file while it waited —
  the decision is refused (`WORKSHOP_CHANGED`) and the page refreshes, so nothing goes public unseen. A credited person
  who takes their own name off a project they can no longer see is sent to `/workshop?left=1` (`stillVisible`).
  **Take off the website / Withdraw**
  (`unpublishWorkshopProject`: APPROVED / PENDING → DRAFT) by anyone who can change it. It's public, so a change by
  someone who isn't a reviewer that **adds or rewrites** something on an APPROVED project — details or credits (saved
  unchanged doesn't count), a new photo, a photo's caption, a new design file — sends it back to PENDING
  (`touchProject`; the services return `sentForApproval`). Removing a photo or file, reordering photos, and picking the
  cover don't. A project on the website (or waiting) keeps at least one photo. **Featured** (`setWorkshopFeatured`,
  reviewers) puts it first in its section. Reviewers see a "Waiting for approval" tab and the nav count
  (`countPendingWorkshop`); no emails.
- **Photos**: PNG, JPG, or WebP by their bytes (`checkWorkshopPhoto`, reusing the poster sniffing and pixel limits;
  HEIC gets its own message), stored **without their metadata** (`stripImageMetadata`: no GPS position, camera, or
  comments — they go on the public website; a JPEG's or PNG's Exif orientation is kept, a WebP's isn't) with the
  matching extension/type and the
  `width`/`height` they're shown at (swapped for orientations 5–8, `imageOrientation`; the website uses them to avoid
  layout shift), in story order (`position`, first version first; `moveWorkshopPhoto` renumbers 0..n-1), with
  an optional `label` ("Version 1") and `note` (what failed / changed). `coverPhotoId` = the photo shown first (null or
  removed = `defaultCoverIndex`: a part's newest version, the last photo; software's and other builds' first). The form
  makes photos over 2000 px or 1.5 MB into a smaller JPG in the browser. At most
  `WORKSHOP_LIMITS.photosPerProject` (12).
- **Design files**: an allowlist of extensions (`WORKSHOP_FILE_EXTENSIONS`: STL, STEP, 3MF, OBJ, F3D, SolidWorks,
  Inventor, IGES, DXF, G-code, PDF, ZIP…; PDFs and ZIP/3MF must start right), stored as `application/octet-stream`
  (PDFs `application/pdf`) and always downloaded from the website. At most `filesPerProject` (8). Bigger than 4 MB →
  the project's CAD link.
- **Storage**: both are stored files (kinds `workshop-photos`, `workshop-files`; migration `20261004100000_workshop`
  with the CHECKs and deletion triggers) under the shared cap, `FileStorageUsage.workshop`; each person's uploads stay
  under `WORKSHOP_FILE_BYTES_PER_PERSON` (60 MB, 10× with R2) unless they have admin access; 60 uploads an hour,

- **Public** (see **Public API for the team website**): `GET /api/public/workshop` (`publicWorkshopResponse` →

## Website Coding (`src/server/services/site-content.ts`, Admin → Website Coding, `/admin/website`)

The owner's ask: future students change the public team website's text, links, and pictures from the portal, never
touching TypeScript, and the site never needs a rebuild for it. The website (its own repo) marks each editable thing
with a **slot key**; the portal stores values per key and serves them; the website's script swaps them in. The shared
contract (keep both repos in step): the website's `src/lib/site-content.ts` and
`src/components/site-content/SiteContent.astro`; the portal's client-safe side is `src/lib/public-site-content.ts`.

- **Slots**: `data-edit-text="<key>"`, `data-edit-link="<key>"` (on an `<a>`: its href), `data-edit-image="<key>"`
  (an `<img>`, or a placeholder box the website fills with an `<img>`), optional `data-edit-label`, and
  `data-edit-multiline` for text that may span lines. Keys: `SITE_KEY_RE` (`^[a-z0-9]+(?:[.-][a-z0-9]+)*$`, ≤ 120),
  by convention `<page>.<section>.<item>` (`home.hero.tagline`, `season.2025-2026.team-photo`, `footer.email`). What the
  website's code says is the **default**; a saved value replaces it; **Reset to original** deletes it. To make something
  new editable, add the attribute in the website's code — nothing changes in the portal.
- **Data** (migration `20261006090000_site_content`): `SiteContent` (`key` @id, `kind` TEXT | LINK | IMAGE, `value` =
  the text / the address / the `SiteImage` id, `updatedBy`), `SiteImage` (a stored file, kind `site-images`, with
  `key`, `width`/`height`, `alt`; the CHECK and the deletion trigger), `SiteContentEdit` (`key`, `kind`, `before` →
  `after`, null = the website's own; `editedBy`).
- **Who**: everyone with admin access (`canEditWebsite` = `canAdminister`; ACTIVE), checked in every service and in
  the queries (`getSiteContentAdminView`, `getSiteImageFile` → null for anyone else).
- **Services**: `setSiteText` (plain text — never HTML, the website applies it with `textContent`; CRLF → `\n`,
  control characters dropped, trimmed, 1–`SITE_TEXT_MAX` 5,000), `setSiteLink` (`parseSiteLink`, **exactly the
  website's `safeLink`**: `https://` / `http://` (normalised, no user:password), `mailto:`, or a site path starting
  with **one** `/`; never `javascript:`, `data:`, `//host`, `/\host`, spaces, control characters; ≤ 2,000),
  `uploadSiteImage({ key, alt, file })`, `setSiteImageAlt` (the description of the picture shown — not an undoable
  change), `resetSiteContent`, `revertSiteContentEdit({ editId })` (puts back the edit's `before` as a new change; a
  picture deleted since → `ConflictError(SITE_IMAGE_GONE)`). Every change writes its `SiteContentEdit` **in the same
  transaction**, all under one advisory lock (`hk-site-content`) so before/after are exact; saving the same value (or
  resetting a spot that isn't changed) is a no-op (`{ changed: false }`, no edit row). At most
  `SITE_CONTENT_MAX_ROWS` (3,000) saved spots (`SITE_CONTENT_FULL`). Rate limits: 300 changes and 60 uploads per person
  per hour. A value of another kind than the one saved (the website changed what the spot is) counts as "original" in
  the edit's `before`.
- **Pictures** (`checkSiteImage`): PNG, JPG, or WebP by their bytes (HEIC: the iPhone hint), ≤ 4 MB, ≤
  `SITE_IMAGE_MAX_SIDE` (8,000) pixels a side, a still picture, metadata stripped in **strict** mode (they're public),
  a JPEG browsers can draw, stored as `picture.<ext>` with the size it's shown at. The editor makes big photos
  web-sized in the browser first (`preparePhoto` from the Workshop: ≤ 2,000 px / 1.5 MB). Under the shared cap
  (`FileStorageUsage.website`, "team website pictures"); no per-person allowance (admins only). Each upload is a **new
  row** (a new public address); a spot keeps its `SITE_IMAGES_KEPT_PER_SLOT` (5) newest pictures for Undo and the
  upload deletes older ones (never the one shown) — the action then calls `scheduleFileCleanup()`.
- **Public** (see **Public API for the team website**): `GET /api/public/site-content` (`publicSiteContentResponse` →
  `getPublicSiteContent`) → `{ enabled: true, updatedAt, texts: { key: text }, links: { key: href }, images: { key: {
  src, alt, width?, height? } } }` — `src` always the relative `/api/public/site-images/<id>`; never who changed what or
  the history. `GET /api/public/site-images/[id]` (`publicSiteImageResponse` → `getPublicSiteImage`: one raw query with
  "a `SiteContent` IMAGE row **of the picture's own key** names it" in its WHERE): inline, immutable, named
  `website-picture.<ext>`; pictures kept only for Undo, reset, or deleted are the uncached 404. Admins see every
  picture at the signed-in `/admin/website/images/[id]`.
- **The editor** (`src/components/admin/website-editor/*`, page `src/app/(app)/admin/website/page.tsx`, actions in
  `actions.ts` next to it): the website in an `<iframe src="<WEBSITE_EDITOR_URL><path>?hk-edit=1">` inside a browser-like
  frame (page menu `SITE_EDITOR_PAGES`, address, reload, computer/phone width), sandboxed
  (`allow-scripts allow-same-origin allow-forms allow-popups allow-popups-to-escape-sandbox`: no top navigation).
  postMessage, both ways checked: the page accepts a message only when `event.origin` is the website's origin **and**
  `event.source` is the frame's own window, and checks it field by field (`parseSiteMessage`); it posts only to the
  website's origin. Website → portal: `{ source: "hk-site", type: "ready", path, title, slots: [{ key, kind, label,
  defaultValue, multiline }] }` (on each page load, and again when spots appear later — handled idempotently: the list

  "preview", texts, links, images }` (the full current content — `buildPreviewMessage`, pictures as absolute addresses

- **Settings**: `WEBSITE_EDITOR_URL` (optional; `env.websiteEditorUrl` / `parseWebsiteEditorUrl`: an http(s) base

### Services (mutations)

```ts
// src/server/services/things.ts
import { z } from "zod";
import type { ServiceContext } from "../context";
import { parseInput } from "../action";
import { ForbiddenError, NotFoundError } from "../errors";

const input = z.object({ title: text("Title", LIMITS.taskTitleMax) });

export async function createThing(ctx: ServiceContext, raw: unknown) {
  const data = parseInput(input, raw as Record<string, unknown>);   // throws ValidationError with fieldErrors
  if (!canDoIt(ctx.actor)) throw new ForbiddenError();
  const thing = await ctx.db.thing.create({ data: { ... } });
  ctx.notifier.notify({ type: "...", ... });                          // after the write succeeds
  return { id: thing.id };
}
```

- Signature: `(ctx: ServiceContext | PublicContext, raw: unknown)`. Validate **inside** the service with zod (so tests cover validation). Use helpers in `src/lib/validation.ts` (`text`, `optionalText`, `stringArray`, `checkbox`, `dateOnlySchema`, `emailSchema`, `idSchema`, `optionalEnum`).
- Browsers send a textarea's line breaks as CRLF, but its `maxLength` counts each as one character: `text` / `optionalText` turn CRLF (and a lone CR) into `\n` before trimming and the length check, so text typed up to the box's limit fits and saved text uses `\n`. A custom `z.string()` for a textarea does the same with `.overwrite(normalizeLineBreaks)` before `.trim()` (question bodies and replies, notebook entries, the sponsor import box).
- Use `ctx.now` (not `new Date()`) and `ctx.config` (not `process.env`) so tests are deterministic.
- Throw the typed errors from `errors.ts`; their messages are shown to users, so write them for humans.
- Multi-step writes → `ctx.db.$transaction(...)`.
- Emit notifications via `ctx.notifier.notify(event)` — never send email directly from a feature.
- Return small plain objects (ids), not raw DB rows.

### Queries (reads for pages)

`src/server/queries/<feature>.ts`, `import "server-only"`, use the `prisma` singleton, take the `Actor`, and **always apply the scope helpers**.
Select only needed columns; `take` a sensible limit (paginate at 50). Return plain serializable data (convert `@db.Date` with `dbToDateOnly`).

### Server Actions

In `src/app/(app)/<route>/actions.ts` with `"use server"` at the top:

```ts
export async function createThingAction(_prev: ActionState, formData: FormData): Promise<ActionState> {
  return runAction(async () => {
    const ctx = await getServiceContext();              // throws UnauthorizedError if not signed in/active
    const { id } = await createThing(ctx, formDataToObject(formData));
    revalidatePath("/", "layout");                      // refresh pages + nav badge counts
    redirect(`/things/${id}`);                           // optional; runAction re-throws redirects
  }, { success: "Saved.", formData });
}
```

- Every action: build the context, call a service, `revalidatePath("/", "layout")` after writes. No business logic in actions.
- Bound args are fine for ids: `action.bind(null, assignmentId)` — but the service must still re-check permissions from the DB.
- Action return values go to the browser: only `ActionState`.

## Resources (`src/server/services/resources.ts`)

A Resource is a link or a small uploaded file (`ResourceFile`, stored in Postgres or Cloudflare R2 — see **File storage**
below — ≤ `LIMITS.resourceFileMaxBytes` = 4 MB each and the team's storage cap in total; Server Action bodies are capped at
5 MB in `next.config.ts`, and Vercel rejects requests over 4.5 MB, so don't raise the file limit).

- People with admin access (`canManageResources`) add resources that go live (APPROVED) and can edit/remove/pin anyone's.
- Everyone else's start PENDING, are only visible to them and reviewers (`canViewResource` / `visibleResourcesWhere`), and are
  approved or turned down (`reviewResource`, `canReviewResources`). A member's edit sends it back to PENDING.
- Files are served only by `src/app/(app)/resources/files/[id]/route.ts` with the headers from `src/server/resources/serve.ts`:
  text as `text/plain`, png/jpeg/gif/webp and PDF inline, everything else (HTML, SVG, …) as an `application/octet-stream`
  download; always `nosniff`, a sandboxing CSP (PDFs skip `sandbox`, which Chrome's PDF viewer refuses), and `no-store`
  (posters, notebook pictures, sponsor logos, and Workshop photos opt into browser caching, `immutable`: their address
  never shows different bytes).
  Windows executables/scripts are refused at upload (`BLOCKED_EXTENSIONS`). Never render uploaded content as HTML.
- Upload checks (`src/server/files/upload.ts`) and the storage cap (`src/server/files/storage.ts`) are shared with sponsor
  files and posters; any new kind of stored file must use `assertFileStorageRoom` so every file counts toward the same cap
  (and `withStoredFiles`, see **File storage**).
  "Full" messages start with `storageFullSentence(usage)` (how much is Resources files vs sponsor files, plus posters,
  notebook pictures, strategy files, sponsor logos, Workshop photos and designs, members' photos, team website pictures, and meeting recordings when there are any) and say who can free each (`posterCleanupSentence(usage)` adds who can remove posters). Usage is shown on Admin → Approvals ("File storage") and on each sponsor's file card (`getFileStorageUsage`).

## File storage (`src/server/files/`)

Every uploaded file (`ResourceFile`, `SponsorshipFile`, `PosterFile`, `NotebookImage`, `StrategyFile`, `SponsorshipLogo`,
`WorkshopPhoto`, `WorkshopFile`, `UserPhoto`, `SiteImage`, `MeetingAudioPart` — kinds `resources`, `sponsors`, `posters`,
`notebook`, `strategy`, `logos`, `workshop-photos`, `workshop-files`, `photos`, `site-images`, `meeting-audio`) keeps its bytes in
**Postgres** (`data`) or in **Cloudflare R2** (`storageKey`, the object's key; `data` null) — a CHECK constraint makes every
row have one. R2 is used only when all four of `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` are set
(`env.r2Status` / `readR2Status`: some missing = `partial`, a bad account id/bucket/endpoint = `invalid`, both mean Postgres;
`R2_ENDPOINT` only overrides the address for tests, https or a local http address, no path — and with
`NODE_ENV=production` only an https `….r2.cloudflarestorage.com` address, so a stray value in Vercel can never send files
elsewhere). Without them everything works as
before (Postgres, 300 MB), so the code is safe to deploy before the owner adds the keys (README step 9).

- **Client** (`object-store.ts`): our own AWS Signature V4 (node:crypto, region `auto`, service `s3`, path-style
  `/<bucket>/<key>`, checked against Amazon's worked examples): `putObject`, `getObject` (a stream), `getObjectBytes`,
  `deleteObject`, with timeouts (20 s to answer; `withTimeout(ms)` gives another). A `getObject` body errors when R2
  sends nothing for that long while we're waiting on it (never because the reader is slow), so a stalled R2 can't hold a
  file route open. Objects are always PUT as `application/octet-stream` + `Content-Disposition: attachment` (never the
  upload's type — we never serve R2's metadata, and a bucket made public by mistake still can't run uploaded HTML/SVG);
  GETs ask for `Accept-Encoding: identity`, and R2's length is dropped if an answer comes packed anyway.
  `ObjectStoreError` messages carry R2's error code and a hint, never the keys, the signature, or the endpoint's secret
  parts; `status` is null when R2 never answered (a timeout, a dropped connection). `getObjectStore()` builds it from the
  settings (null = Postgres); services get it as `ctx.objectStore` (`getPublicContext`; tests leave it out = Postgres).
- **Keys** are made by the server only: `newStorageKey(kind)` = `<kind>/<24 random url-safe characters>` (144 bits); the
  client refuses anything else (`isStorageKey`), so no filename or user input ever reaches R2.
- **Writing** (`stored.ts`): services store uploads through `withStoredFiles(ctx, kind, uploads, save)`. With R2 it uploads
  first — never inside a transaction or under the storage lock — then calls `save(columns)`, which creates the rows by
  spreading each column set (`filename, contentType, size, data, storageKey`: always both of the last two, so a replaced
  file never keeps an old key or old bytes). Before uploading, the key is *reserved* in `FileDeletion` (due in an hour) and
  taken off once the row is saved (`confirmStorageKeys`), so an upload whose row never gets saved (a crash, a timeout) is
  deleted later anyway. An upload R2 refuses → `FILE_UPLOAD_FAILED` on the `file` field (strategies: `files`), no row;
  what was uploaded is deleted right away, except an upload R2 never answered (`uploadMayStillLand`): it may still be
  saved after we gave up, so its key is due in 10 minutes (`deferStorageKeys`) and the drain deletes whatever landed
  (`settleFailedUploads` picks). If `save` throws (a check under the lock, the database), the uploaded objects are
  deleted right away or queued (`releaseStorageKeys`). All checks (types, sizes, rate limits, caps) stay in the
  services, unchanged; each service also passes them as `withStoredFiles(…, { precheck })`, run without the lock
  (`checkFileStorageRoom`, `locked: false`) before uploading to R2, so an upload that would be refused (storage full, a
  full sponsor/entry/strategy, an allowance) is never sent to R2 and deleted again. The check under the lock stays the
  real one.
- **The cap** (`storage.ts`): `fileStorageCapBytes(usesObjectStorage(ctx))` = 300 MB (`LIMITS.resourceStorageMaxBytes`) in
  Postgres, 8 GB (`OBJECT_STORAGE_CAP_BYTES` = 8 GiB, over 1 GB under R2's free 10 GB however it's counted) with R2; each person's allowance
  (`POSTER_FILE_BYTES_PER_PERSON`, `SPONSOR_FILE_BYTES_PER_PERSON` — sponsor files and logos together —
  `NOTEBOOK_IMAGE_BYTES_PER_PERSON`,
  `STRATEGY_FILE_BYTES_PER_PERSON`, `WORKSHOP_FILE_BYTES_PER_PERSON` — Workshop photos and design files together —
  `MEMBER_UNAPPROVED_FILE_BYTES`) goes through `perPersonFileCap(base, objectStorage)`
  (10× with R2) — messages show that number. `assertFileStorageRoom(tx, change, message, objectStorage)` still sums the rows'
  `size` under the one advisory lock, wherever the bytes are. `formatFileSize` shows GB ("8 GB").
- **Reading**: file routes select `STORED_FILE_SELECT` and answer with `sendStoredFile(request, row, options)` (`respond.ts`):
  Postgres bytes as before, an R2 object **streamed through our response** with exactly the same headers (strategy files
  pass `headers: strategyFileHeaders`; the public sponsor-logo route passes `publicFileHeaders`). Never redirect to R2,
  hand out R2 URLs, or make the bucket public. R2 not set up →
  503, R2 failing → 502, object missing → 404 (plain text, `no-store`). Server-side reads (the Resources text preview —
  `reason: "unavailable"` when it can't be read — and the notebook's Word export via `loadNotebookImageBytes`) use
  `readStoredBytes`.
- **Deleting**: database triggers (migration `20260928090000_object_storage`; `20261004080000_sponsor_logos` for logos;
  `20261005070000_user_photos` for members' photos; `20261006090000_site_content` for Website Coding pictures;
  `20261007090000_meeting_recaps` for meeting recordings) put a
  row's `storageKey` into `FileDeletion` whenever the row is deleted — directly or by any cascade (a sponsor — its files and
  logo — notebook, page, entry, poster, strategy, league team, an account's photo, a meeting recap)
  — or its key changes. The app only drains that queue: actions that delete or replace files call `scheduleFileCleanup()`
  (`cleanup.ts`, `after()`: deletes from R2 after the response; never fails the action), the owner's storage card drains
  what's waiting when it's shown, and it has **Clean up**. `drainFileDeletions(db, { store, limit, budgetMs, includeStuck })`
  never throws: keys a row still uses are only taken off the list, a failed delete counts an attempt and waits (ones that
  keep failing go last; after `FILE_DELETION_MAX_AUTO_ATTEMPTS` only the owner's Clean up, `includeStuck`, tries them, and
  the card counts them apart). The "still in use?" check (`KEY_IN_USE`) locks the row it finds (`FOR KEY SHARE`), so it
  waits for a delete or key change that hasn't committed yet instead of dropping the queue entry that delete's trigger
  found already there; `confirmStorageKeys` does one key per statement (never holding one row's lock while waiting for
  another). `FileDeletion.createdAt` = when it may be deleted (reservations: an hour ahead; unanswered uploads: 10
  minutes); the column has no time zone, so it's only ever written and compared in SQL with `CURRENT_TIMESTAMP` (never
  through Prisma with a JS Date).
- **Owners' tools** (`services/file-storage.ts`, `canManageFileStorage` = owners; Admin → Approvals → File storage, whose
  page sets `maxDuration = 60`): **Test connection** (`testFileStorage`: save, read back, delete a `connection-test/…`
  file; says which step failed), **Move N files to R2** (`moveFilesToObjectStorage`: a few rows at a time, each uploaded and
  then switched with a conditional update — only if the row still has no key and the same bytes, `sha256(data)` — so a
  file replaced or removed meanwhile is never overwritten; stops starting files after 25 s or 3 R2 errors in a row; click
  again to continue), **Clean up** (`cleanUpFileStorage`, 25 s). They use R2 with `ADMIN_TOOL_TIMEOUT_MS` (10 s) per
  request and never send a delete right after an unanswered upload, so a click ends well inside 60 s even with a slow R2.
  Everyone with admin access sees usage, where new files go, and how many files are where (`getFileStorageOverview`);
  `owner` (the settings' state, what's waiting, the tools) is null for everyone but owners.
- **Adding a new kind of stored file**: a migration with the same `data`/`storageKey` columns, CHECK, and trigger; then
  `FILE_KINDS`, the key pattern, and `KEY_IN_USE` in `object-store.ts`, `FILE_TABLES` and `fileStorageUsage` in
  `storage.ts`, `withStoredFiles` in its service, `sendStoredFile` in its route, and `scheduleFileCleanup()` in its
  deleting actions.
- **Tests**: `tests/helpers/fake-s3.ts` is an in-memory S3 server that verifies each request's signature and can fail,
  hang, delay, or run a hook; use `{ ...contextFor(db, actor), objectStore: s3.store() }` for R2 mode
  (`tests/file-storage-r2.test.ts`, `tests/object-store.test.ts`). `tests/setup-env.ts` clears the R2_* settings, so no
  test ever reaches a real bucket.

## Notifications (email)

Services emit `NotificationEvent`s (see `src/server/notifications/events.ts`). `src/server/notifications/deliver.ts` decides recipients
(respecting each user's `emailOn*` preferences, skipping the person who caused the event) and sends via `sendEmail()`, which writes `EmailLog`.
Production sends run in `after()` so user actions never wait on SMTP.

| Event | Emitted by | Recipients (pref) |
|---|---|---|
| `question.asked` | questions | `recipientId` if set; else ACTIVE leaders of `subteam`; if subteam null → ACTIVE captains (`emailOnQuestion`) |
| `question.replied` | questions | staff replied → asker (`emailOnReply`); asker replied → recipient or subteam leaders/captains + staff who already replied (`emailOnQuestion`) |
| `task.submitted` | checklist | task creator if they can still review it; otherwise the first non-empty tier of reviewers: leaders of the task's subteam (whole-team task: of the submitter's subteam) → captains → admins (`emailOnSubmission`) |
| `task.reviewed` | tasks | assignee (`emailOnReview`) |
| `task.assigned` | tasks | the new assignees, except whoever made the change (`actorId`) (`emailOnAssigned`, default off) |
| `account.pending` | auth | everyone with admin access: ACTIVE owners, leaders, captain, mentors, teachers (`emailOnSignup`) |
| `account.approved` | admin | that user (always) |
| `password.reset` | auth/admin | that user (always) |
| `password.changed` | auth/settings | that user (always, security notice) |
| `resource.submitted` | resources | ACTIVE owners + leaders of the member's subteam (captains if the member has no subteam or it has no active leaders), never the member (`emailOnResource`) |
| `resource.reviewed` | resources | the member who shared it (`emailOnReview`) |

`question.asked` / `question.replied` are also posted, in full, to a leaders-only Discord channel when `DISCORD_WEBHOOK_URL` is set (`src/server/notifications/discord.ts`; one-way, logged in EmailLog as `to = "Discord"`, `allowed_mentions` empty so user text can't ping anyone).
`attendance.no_shows` (attendance, when a runner closes a session while people who said they'd come aren't on the list — never the person who started it) is **Discord-only** (no email): "Regular attendance · Tue, Sep 29" linking to the session, "3 said they'd come but didn't check in: A, B, C" (names escaped; people put on the list since it closed are left out; nothing when nobody's left). Delivery never throws (`postToDiscord`), so closing never breaks.

## Tests

- `tests/<feature>.test.ts`, real Postgres. Pattern:
  ```ts
  let t: TestDb;
  beforeAll(async () => { t = await createTestDb(); });
  afterAll(async () => { await t.drop(); });
  const leader = await makeUser(t.db, { role: "BUILD_LEADER" });
  const ctx = contextFor(t.db, leader);               // ctx.notifier.events collects notifications
  ```
  Helpers: `tests/helpers/db.ts` (`createTestDb`), `tests/helpers/factories.ts` (`makeUser`, `makeTask`, `contextFor`, `publicContext`, `TEST_NOW`, `TEST_TODAY`, `TEST_PASSWORD`).
- Test the service layer: happy paths, validation errors, **permission denials for each role that must be denied**, state-machine conflicts, and emitted events.
- Run only your file while developing: `npx vitest run tests/<feature>.test.ts`.
