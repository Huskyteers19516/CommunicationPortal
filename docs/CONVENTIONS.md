# Huskyteers Portal — engineering conventions

Team communication app for FTC 19516 The Huskyteers (Anaheim, CA). ~30–40 users.
**English only** (no i18n, no Chinese text in the UI).

Stack: Next.js 16 App Router (Server Components + Server Actions) · React 19 · Tailwind v4 · Prisma 7 (`prisma-client` generator, `@prisma/adapter-pg`) · PostgreSQL · zod 4 · vitest.

> Next.js 16 differs from older versions. Check `node_modules/next/dist/docs/` when unsure
> (e.g. `proxy.ts` replaced `middleware.ts`; `params`/`searchParams` are Promises; `PageProps<'/route/[id]'>` and
> `LayoutProps` are global types generated by `next typegen`).

## Local environment

- Postgres: `npm run db:start` (embedded Postgres on port 54329; already running during development). Dev DB = `portal`.
- `npm run typecheck` (runs `next typegen` + `tsc`), `npx eslint <paths>`, `npm test` (vitest).
- **Never** run `prisma migrate reset`, drop databases other than your own test DBs, or change `prisma/schema.prisma`.
  If you truly need a schema change, stop and report it.
- Don't run `next build` or `next dev` concurrently with other agents unless told to; typecheck + lint + vitest are enough.

## Roles & permissions (source of truth: `src/server/permissions.ts`, mirrored in `src/server/scopes.ts`)

| Role | Subteam | Needs admin approval | Scope |
|---|---|---|---|
| MEMBER | required: SOFTWARE / BUILD / BUSINESS | no (ACTIVE on sign-up) | own checklist, ask questions |
| SOFTWARE_LEADER / BUILD_LEADER (×3) / BUSINESS_LEADER | implied by role | yes | manage own subteam: tasks, review, answer questions |
| CAPTAIN | none | yes | all subteams + whole-team tasks |
| MENTOR / TEACHER | none | yes | all subteams + whole-team tasks |
| `isAdmin` flag (**owner**, shown as "Owner") | any role | — | everything above + owners' accounts + granting Owner |

- **Admin access** (`canAdminister`) = every leader, the captain, mentors, teachers, and owners: the Admin area (approve sign-ups and member resources, manage people, email log). It does **not** widen task scope — subteam leaders still only manage their own subteam's tasks.
- **Guardrails on admin access** (`ROLE_RANK`: members < subteam leaders < captain/mentors/teachers < owners):
  non-owners manage only ACTIVE accounts ranked **below** them and sign-ups waiting for approval **up to** their own rank
  (`canManageAccount`), and can only give positions below their own (up to their own when approving a sign-up —
  `canGrantRole` / `grantableRoles`). They never see password-reset links (email only), never change someone else's
  email, can't change their own position, and never touch owners' accounts or the Owner flag. The email log is owners-only
  (`canViewEmailLog`, `requireOwnerUser`). There must always be at least one ACTIVE owner.
- **Owners** (`isAdmin`, `isOwner`) can do all of the above for anyone, including other owners.
- `ADMIN_EMAILS` only bootstraps the first owner: while no ACTIVE owner exists, registering/signing in with a listed email makes that account an ACTIVE owner. Afterwards owners are managed in Admin → People (or `npm run admin`).

- **staff** = any leader/captain/mentor/teacher or admin (`isStaff`). **all-scope** = captain/mentor/teacher/admin (`hasAllScope`).
- Seats: `SEAT_LIMITS` in `src/lib/constants.ts` (1 captain, 1 software, 3 build, 1 business leader).
- Everyone (including leaders) can be assigned tasks and has a Today checklist.
- Nobody reviews their own submission unless all-scope.
- Whole-team tasks (subteam null) are created/edited only by all-scope staff, but **subteam leaders also review their own members' items** on them (`canReviewAssignment(actor, task, { userId, assigneeSubteam })`, mirrored by `reviewableAssignmentsWhere` / `reviewQueueWhere`).
- Members only see their own questions; staff see questions in their scope.
- **Every service must enforce permissions itself** by calling functions from `permissions.ts` (or filtering with `scopes.ts`). UI hiding is not security.

## Checklist lifecycle (`src/server/domain/assignment.ts`)

`Task` = what a leader assigns (title, description, subteam|null, dueDate DATE, priority, creator).
`TaskAssignment` = one person's checklist item for a task: `TODO → SUBMITTED → APPROVED` (officially done) or `→ REJECTED` (sent back with a note) → `SUBMITTED` again. Members can withdraw `SUBMITTED → TODO`. Managers can reopen `APPROVED → TODO`.

- Use `canTransition` / `allowedFrom` and do **conditional** writes to avoid races, e.g.
  `db.taskAssignment.updateMany({ where: { id, status: { in: allowedFrom("approve") } }, data })` and treat `count === 0` as a `ConflictError`.
- On submit: `status=SUBMITTED, submittedAt=now, submissionNote=note|null` (keep the old `reviewNote` so reviewers can see prior feedback).
- On approve/reject: `status, reviewedById=actor, reviewedAt=now, reviewNote=note|null`. Reject **requires** a note (tell them what to fix).
- On withdraw: `status=TODO, submittedAt=null, submissionNote=null`. On reopen: `status=TODO`, clear `reviewedAt/reviewedById`, keep `reviewNote`.

## Categories, sign-up tasks, and the Task dashboard

- `TaskCategory` groups a subteam's tasks (`subteam` null = whole-team categories), managed by `canManageCategories`
  (= `canManageSubteam`) in `services/categories.ts` (writes to one subteam's list take an advisory lock: names are unique
  per subteam, case-insensitively, max `LIMITS.categoriesPerSubteamMax`). A task's category must belong to its subteam.
- A task is either **"Assign people"** (`signupMode = false`) or **"Let people sign up"** (`signupMode = true`, optional
  `signupLimit` = most people on it, counting everyone). `signupOpen` closes/reopens sign-ups without changing the mode
  (`setSignupOpen`); editing a sign-up task keeps it open/closed as it was. Switching to "Assign people" clears `selfAssigned`.
- `services/signups.ts`: `signUpForTask` / `leaveTask`. Sign-ups and task edits lock the task row (`SELECT … FOR UPDATE`)
  before counting people, so the limit holds under races. Leaving is only for your own self sign-up while it's TODO.
- `updateTask` gets `previousAssigneeIds` (+ `previousAssigneeIdsSent`) from the edit form: changes are computed against the
  people the form showed, so sign-ups that happened while the form was open are kept.
- `/tasks` (Task dashboard) and `/tasks/[id]` are for every ACTIVE user (`queries/board.ts`). They show who's on each task
  with a **public** status only (done / checked off / to do — "sent back" shows as to do) and never notes.

## Sponsorships (`src/server/services/sponsorships.ts`, `/sponsors`)

The Business team's sponsor tracker (replaces their spreadsheet). Only the Business subteam and staff can see or change it
(`canUseSponsorships`; pages show everyone else a short explanation, never data); deleting is for whoever added it, the Business leader, and all-scope
staff (`canDeleteSponsorship`; the Business leader and all-scope staff are `canManageSponsorships`). Stages: Haven't started → Do soon → Needs work → Submitted → Accepted / Declined → Finished.
Moving into Submitted/Accepted fills that date with today (team timezone) only if it's empty. `amountReceived` is whole
dollars (`src/lib/money.ts`). "Info for applications" is a `TeamNote` (key `sponsorship-info`) — never store passwords in it (the card warns, without blocking the save, when `mentionsPassword` in `src/lib/sponsorships.ts` matches).
The edit form sends `version` (the `updatedAt` it loaded): a stale save is a `ConflictError`, so it can't undo a stage change
made from the list meanwhile (the list's stage menu itself is last-write-wins and only writes the stage and an empty date).
Field validation lives in `src/lib/sponsorship-fields.ts` (client-safe). `/sponsors/import` parses rows pasted from a sheet
with the same pure parser and field checks on the client (preview) and the server (`src/lib/sponsorship-import.ts`; bounded:
1,000 rows, 40 columns, 300k characters, all read before the import lock), then imports all-or-nothing — optionally
updating sponsors already here from the sheet's non-empty cells.
Each sponsor can have attached files (`SponsorshipFile`, `services/sponsorship-files.ts`; e.g. a paper application form to
print, or the filled-out copy): up to `LIMITS.sponsorFilesMax` per sponsor, checked like Resources uploads
(`src/server/files/upload.ts`) and counted toward the same storage cap (`src/server/files/storage.ts`: one advisory lock,
both tables summed). Each person's sponsor files stay under `SPONSOR_FILE_BYTES_PER_PERSON` (50 MB, checked under the same
lock) unless they `canManageSponsorships`, so one account can't fill the storage. Everyone who can use Sponsorships adds
and downloads them (served only by `src/app/(app)/sponsors/files/[id]/route.ts` with the Resources headers; 404 for
everyone else); removing one is for its uploader and whoever can delete the sponsor (`canDeleteSponsorshipFile`).
Deleting a sponsor deletes its files (its Remove question says how many). The card uploads as soon as a file is picked
(nothing is left behind when the edit form is saved), and its actions `refresh()` the page when they fail, so a stale
page catches up. The list's **Select** mode removes several at once
(`deleteSponsorships`: 1–200 ids in one transaction, only the ones the person `canDeleteSponsorship` — the rest are named back,
ids that don't exist only counted — and one count toward the hourly write limit; "Select all" stops at `SPONSORSHIP_BULK_REMOVE_MAX`).

## Parts queue (`src/server/services/parts.ts`, `/parts`)

What needs to be 3D printed, laser cut, CNC'd, cut, or machined, in priority order (`Part.position`, smaller = sooner).
Everyone ACTIVE can add parts and claim one ("I'll make it": NEEDED → CLAIMED, conditional write so only one person wins).
The claimer (or a manager) drops it (→ NEEDED, keeps its place) or marks it done (→ DONE). Managers (`canManageParts`: Build
leaders + all-scope staff) reorder (up/down/top, advisory lock + renumber), edit/remove anything, and put done parts back
(end of the queue). Requesters edit/remove their own part until someone claims it (`canEditPart`). No emails.
Filters: process chips plus `?who=making` (claimed by me — Today's "You're making N parts" links here) and `?who=asked`;
counts follow the active filters, ranks always come from the full queue. File links get `https://` added when missing.

## Posters (`src/server/services/posters.ts`, `/posters`)

The team's posters and flyers. Everyone ACTIVE sees them and adds one directly (no approval); whoever added it and everyone
with admin access edit/remove it (`canEditPoster`). A poster needs an uploaded file (`PosterFile`, one per poster) or an
http(s) design link (`https://` added to a bare `canva.com/…`), or both; `event` + optional `eventDate` (`@db.Date`, at most
5 years back / 2 years ahead; an edit that keeps the saved date isn't re-checked) drive the tabs: **Upcoming** = no date or today and later (newest first), **Past** = earlier
(latest event first), plus `?who=mine`; 48 per page (`queries/posters.ts`, metadata only, never bytes). Files are checked by
their **contents** (magic bytes), not the name: PNG, JPG, GIF, WebP, or PDF only (SVG/HTML/HEIC are refused, with a HEIC
hint; a PDF must start with `%PDF-`, only blank bytes before it), pictures must have a readable pixel size of at most
`POSTER_IMAGE_MAX_SIDE` (12,000) a side and `POSTER_IMAGE_MAX_PIXELS` (50 million) in all (read from the header, GIFs
including every frame, so a tiny file can't freeze everyone's phone), stored with the matching extension and type, ≤ 4 MB,
under the shared storage lock and cap, and each person's poster
files stay under `POSTER_FILE_BYTES_PER_PERSON` (50 MB) unless they have admin access. Creates (and edits that bring a new
file) are rate-limited (`POSTER_RATE_LIMIT`, 30/hour). Editing can replace the file (a new `PosterFile` row, so its URL
changes) or remove it (`removeFile`). Served by `src/app/(app)/posters/files/[id]/route.ts` (PosterFile id, any ACTIVE user,
Resources headers, except inline responses are `immutable`: `private, max-age=604800`, safe because a file id never shows
different bytes, so the grid isn't downloaded again on every visit). The form keeps the picked file in client state (browsers
clear file inputs after a failed save), checks size/type before sending (`src/lib/posters.ts`), makes a PNG/JPG/WebP over
4 MB into a smaller JPG in the browser (`components/posters/shrink-picture.ts`), previews pictures (one the browser can't
show is taken off), and drops a picked file the server refused. Deleting a poster deletes its file. No emails.

## Fundraising (`src/server/services/fundraising.ts`, `/fundraising`)

Fundraisers (car wash, bake sale, donation page…) with a kind, status (Planning → Upcoming → Happening now → Done, or
Cancelled), dates (`startsOn`/`endsOn`, `@db.Date`; no end date = one day; within 5 years back / 2 years ahead so a year
typo like 0026 is caught — an edit may keep a date it already has), location, an http(s) link, a goal and amount
raised (whole dollars via `src/lib/money.ts`), a lead (must be ACTIVE; an edit may keep a lead who left), and an optional
number of helper spots. Everyone ACTIVE sees them and taps **I'll help** / **Leave**; the Business subteam and staff
(`canManageFundraisers`) add, edit, remove, update the amount raised, take people off the helper list (any time), and set
the season goal and start (`TeamNote`s `fundraising-season-goal` — empty = the page adds up each fundraiser's goal — and
`fundraising-season-start`: only fundraisers whose last day is on or after it count toward the totals; empty = all-time).
Helping and leaving are only while it's open (`fundraiserClosedReason` in `src/lib/fundraising.ts`: not Done/Cancelled and
its last day, team timezone, hasn't passed); open ones whose dates passed are listed apart ("Dates passed") until someone
marks them done. Sign-ups and edits lock the fundraiser row (`SELECT … FOR UPDATE`) before counting helpers — only ACTIVE
ones count and are listed while it's open — so the spots limit holds under races and an edit can't set fewer spots than
people signed up. The edit form sends the amount raised it loaded (`loadedRaisedAmount`): left as is, a newer amount from
the quick box is kept; changed while someone else changed it, the save is refused on that field and the page refreshes so
saving again replaces it. Totals leave out cancelled fundraisers. No emails.

The top of the page is the **Path planner**: the owner's Pedro Pathing visualizer (BIOBUZZ edition, a Svelte app on

## Order list (`src/server/services/orders.ts`, `/orders`)

What the team needs to buy (replaces the Business team's "Purchase List" sheet). `PurchaseItem`: description, notes (SKU,
where to find it), an http(s) product link (`https://` added to a bare `andymark.com/…`), vendor, optional quantity
(1–`LIMITS.purchaseQuantityMax`), cost for the whole line in **cents** (`costCents`; typed in dollars and read by
`parseCents` in `src/lib/orders.ts` — the `parseDollars` formats, but keeping the cents, up to $100,000), "For"
(`subteam`, null = whole team), status, orderer. Everyone ACTIVE sees every item and adds items (orderer = themselves).
Managers (`canManageOrders`: everyone with **admin access** — accounts someone approved; the self-chosen Business
subteam is not enough to approve spending) set any status (including **Approve**), edit/remove anything, and pick the
orderer (an ACTIVE person, or no one yet; an edit may keep one who left). **Nobody approves their own request** unless
all-scope: from Requested or N/A, an item a leader added only goes to N/A/Requested for them (`purchaseStatusTargets`),
and only all-scope staff add an item with another status (`canAddPurchaseWithStatus`). Everyone else edits/removes items
they added or order while **Requested** (`canEditPurchase`; conditional writes, so an approval that lands first wins); the
orderer **and the Business subteam** (who buy for the team) move an item one step along Approved → Ordered → Done and
back — never approve, mark N/A, or send it back to Requested. Removing is permanent (the confirm points past-Requested
items to N/A instead). **Out-of-date pages:** the status menu sends `from` (the status it showed) and `seen` (the item's
`updatedAt`); every status write is conditional on the status it was checked on, a stale `from` is refused with
"X just changed it to Y." (never "undo someone's Ordered"), and leaving Requested needs `updatedAt = seen` (nobody
approves an edit they haven't seen). The edit form sends `seen` too: a save over someone else's change is refused once
(`ORDER_EDIT_CONFLICT`, the page refreshes, saving again keeps this version); non-managers' edits never write the orderer.
Every status change writes `statusChangedAt/By` (the item's page shows "Status changed by X · time"). Writes are
rate-limited per person (`ORDER_WRITES_PER_HOUR` 120, adds also `ORDER_ADDS_PER_HOUR` 30). No emails: Today shows
"N approved items for you to order" to orderers and "N items to approve on the order list" to the Business leader and
the captain (`countOrdersToApprove`, not their own requests unless all-scope).
The list (`queries/orders.ts`): Open (Requested/Approved/Ordered, oldest first) / Done / N/A (latest change first) / All
tabs with counts, "For" chips (`?for=SOFTWARE|BUILD|BUSINESS|team`; the chosen chip is scrolled into view on phones),
`?mine=1` (added or ordering), and a summary line for the tab (`orderSummaryText`: open items, waiting for approval, to
order, estimated total of the priced open items + how many have no price, or "No prices yet"; Done: count + total; N/A:
count) that follows the For/Mine filters. Desktop: a table (Notes/Qty/For/Added columns from `xl`, folded into
Description below); phones: cards whose title opens the item's page ("Product page ↗" is its own link, notes clamped
to 3 lines, "Orderer: X"). The status is an inline colored menu (`components/orders/status-select.tsx`, the sponsor stage
menu's 600 ms debounce + flush on leave, the list keeps its order, focus moves on when a row leaves the filter — after a
refused change too, saying why — and to the badge when a refused change turns the menu into one) showing only the
statuses the viewer may pick — a badge when none. **Export to spreadsheet** (`/orders/export`, a route handler, any
ACTIVE user, the page's filters, named after them: `order-list-software-open-2026-09-24.csv`) sends a UTF-8 CSV with the
sheet's first columns (Orderer, Status, Description, Notes, …); `csvCell` puts a `'` before text starting with `=`, `+`,
`-`, `@` (or tab/CR) so a spreadsheet never runs it. After a removal the list shows `?removed=1` ("Item removed.", on the
tab the item was on) — never text from the link.

## Attendance (`src/server/services/attendance.ts`, `/attendance`)

Taking attendance with a rotating QR code, "Coming?" answers, day plans, and two-week reports.

- **Who**: `canRunAttendance` (teachers, the Business leader, the captain, mentors, owners) start/close attendance, add or
  remove people by hand (`MANUAL`, `markedBy`; works on closed/past sessions too, to fix the list), write "What we did",
  delete a session started by mistake, and change the schedule (`/attendance/settings`). Sessions more than
  `ATTENDANCE_EDIT_DAYS` (7) days old can only be changed by teachers, mentors, and owners (`canFixOldAttendance`,
  `canEditSessionOn`); the live screen shows them read-only to other runners. `canPlanAttendance` (all staff) see
  **Who's coming** (`/attendance/plan`), write a day's plan, and read reports (`/attendance/reports`). Everyone ACTIVE checks
  in and answers "Coming?" for themselves. Members get 404 on session and report pages (and the CSV) and are sent back from
  plan/settings/the reports list.
- **Fixing mistakes**: `deleteSession` removes today's session, or an earlier one nobody checked in to themselves (only
  `MANUAL` records), with a conditional `deleteMany` (records cascade), so a mis-tap doesn't count as "held". Start asks
  first on a day without regular practice. "What we did" and day plans send back the saved text the form started from
  (`base`): if it changed meanwhile the save is a `ConflictError` and the form shows their text ("Use theirs"); forms that
  must keep typing (these, the schedule) submit with `onSubmit` + `startTransition` so React's form reset can't undo edits.
  Accounts with attendance history can't be deleted (`NO_ACTIVITY` in `services/admin.ts`); disable them instead.
- **Sessions**: `AttendanceSession` is unique per `(date, kind)` — one REGULAR and one FLEX per team-timezone day.
  `openSession` creates today's, reopens a closed one with a **fresh random secret** (old codes stop working), or returns the
  open one unchanged. Check-ins only go into **open sessions of today**; `AttendanceRecord` is unique per person, so a
  second scan returns `already: true` ("You're already checked in ✓").
- **Codes** (`src/server/attendance/codes.ts`, pure): 30-second slots. QR token = `<sessionId>.<slot base36>.<HMAC-SHA256(secret,
  "qr:<id>:<slot>") first 16 bytes, base64url>`, accepted up to 10 slots old (~5 min, so a sign-in redirect still lands) and
  one slot ahead (clock skew). A forged signature is "invalid", never "expired". The 6-digit code is HMAC-derived per slot
  and accepted for the current slot and 3 before (~1.5–2 min); it's matched against today's open sessions only, attempts
  are rate-limited per person (`CODE_ATTEMPT_LIMIT`, 10 per 10 min; format errors don't count), and all comparisons are
  constant-time. **The secret never leaves the server**: the projector page fetches `{ svg, code, expiresAt, expiresInMs }`
  from `getLiveCodeAction` (runners only, open sessions of today; SVG made with `qrcode`, shown as a `data:` image) again
  right after it runs out (`expiresInMs`, so the browser's clock doesn't matter). Anyone with a fresh link or code checks in:
  the live screen reminds runners to compare "Checked in" with the headcount, and full screen lists the latest names.
- **Scan page** `/attendance/scan/[token]` only **reads** on GET (`getScanLanding`: signature, age, session, already in?);
  `<ScanCheckIn>` sends `checkInWithTokenAction` **once** after mount, so prefetching or reloading never writes. It's the same
  element whether or not I'm already in (`alreadyCheckedIn`, read once on mount), so the refresh after its own check-in
  keeps it mounted and it shows "You're checked in for Regular ✓" (focused). Signed-out people go through the proxy's
  `/login?next=…` and come back; with a stale cookie, `requireActiveUser` builds `next` from the proxy's `x-hk-path`

## Team notebook (`src/server/services/notebook.ts`, `/notebook`)

The team's engineering notebooks, laid out like the team's Google Doc outline: **notebooks** (title, emoji, description,
`subteam` = whose it is, null = whole team) → **pages** → dated **entries**. Everyone ACTIVE reads, writes entries, and
exports. The captain and other all-scope staff add, edit, reorder, and delete notebooks (`canManageNotebooks`) and, while
there are none, make the usual ones in one click (`createStandardNotebooks`, `STANDARD_NOTEBOOKS` in `src/lib/notebook.ts`:
Hardware 👷 Build → Intake, Outtake; Software 🧑‍💻 → Competition, Prototyping, Transfer; Business 🧑‍💼 → Outreach,
Sponsorships, Engineering Journal; a ConflictError once any notebook exists). A notebook's pages are added, renamed,
reordered, and deleted by all-scope staff plus the leaders of its subteam (`canManageNotebookPages`). Reordering (notebooks,
and each notebook's pages) takes an advisory lock and renumbers 0..n-1; deleting cascades (the confirm names how many pages
and entries go). Limits: `NOTEBOOKS_MAX`, `NOTEBOOK_PAGES_MAX`, the `LIMITS.notebook*` lengths.

- **Stamps come from the server**: `createNotebookEntry` sets `authorId` and `createdAt = ctx.now`, never from the form.
  Whoever wrote an entry and its notebook's page managers change or delete it (`canEditNotebookEntry`; subteam leaders
  not entries by the captain, mentors, teachers, or owners). Every change to
  the title/text (`updateNotebookEntry`, row locked `FOR UPDATE`) writes a `NotebookEntryEdit` (editor, `editedAt`, the
  previous title and text) and sets `lastEditedById/At`; saving it unchanged writes nothing (`changed: false`, and it
  doesn't count toward the rate limit). Last save
  wins — nothing is lost, it's in the history. The page shows "Written by Ethan Chen · Sun, Sep 27, 2026, 3:42 PM"
  (`formatStamp`, team timezone), "Edited by …", and **History (N)**: the 20 newest changes, loaded when it's opened
  (`getNotebookEntryHistory` via `/notebook/entries/[id]/history`, JSON), each labelled by what it did
  (`notebookChangeLabel`: title / text / pictures) with what it said before (long ones folded). Whoever can change the
  entry can take an old version's text out (`clearNotebookEntryVersion`: blanks it, `isClearedNotebookVersion`; who and
  when stay).
- Entry text is plain text: `NotebookText` renders it with `RichText` (links, line breaks) and turns runs of "- " lines
  into a bulleted list (`notebookBlocks`, shared with the print view and the Word export). Entries are rate-limited
  (`NOTEBOOK_WRITE_RATE_LIMIT`, creates + edits).
- **Pictures** (`NotebookImage`, `addNotebookImage` / `removeNotebookImage`, whoever can change the entry): PNG, JPG, GIF,
  or WebP only, checked by their bytes with the posters' sniffing and pixel-size checks (`checkNotebookPicture`; stored
  with the real type, matching extension, and width/height), ≤ 4 MB, ≤ `LIMITS.notebookImagesPerEntry` per entry, under the
  shared storage lock and cap, and each person's pictures (on entries they wrote) under `NOTEBOOK_IMAGE_BYTES_PER_PERSON`
  unless they manage that notebook's pages; `NOTEBOOK_IMAGE_RATE_LIMIT` per hour. Adding or taking one off marks the entry
  "Edited by" and writes a history row with the text unchanged ("changed the pictures"; one row per person per
  `NOTEBOOK_PICTURE_EDIT_MERGE_MS`) — except by its author within `NOTEBOOK_WRITING_WINDOW_MS` of posting it, before
  anyone edited it (the editor uploads pictures right after the text). Served by `src/app/(app)/notebook/images/[id]/route.ts` (any ACTIVE user,
  Resources headers, `immutable` like posters).
- **Editor** (`components/notebook/entry-editor.tsx`): shows "You · <live time>" the moment it opens; title optional; the
  text and title are controlled, so they survive errors (focus goes to the first invalid field). Picked pictures are made
  JPGs of at most 1280 px (`prepare-picture.ts`; small PNG screenshots and GIFs are kept, WebP always converted), previewed,
  and can be taken off; on save the text goes first (`createNotebookEntryAction` returns `entryId`), then removals, then
  one upload per picture (each request stays under the 4.5 MB limit). A failed picture leaves the entry saved and the
  editor open with that picture to retry or take off. Escape (not while an input method is composing) and Cancel ask
  before throwing away unsaved changes, leaving the page warns (`beforeunload`), and a new entry's text is kept per page in
  this browser until it's saved or discarded (`entry-draft.ts`, localStorage). `EntryRegion` announces results
  (role="status") and moves focus to the saved entry (or "New entry" when it's on another screen), or on after a delete.
- **Export** (each notebook and each page): **Word (.docx)** — route handlers `/notebook/n/[id]/export` and
  `/notebook/p/[id]/export`, built by `src/server/notebook/docx.ts` with `docx` (title page with the team, notebook, and
  export date; each page a Heading 1 on a new page; each entry a Heading 2 with the stamp line, text, pictures scaled to
  the page, and "Edited by … on …"; file name like `Hardware Notebook 2026-09-27.docx`). Only
  `NOTEBOOK_EXPORT_IMAGE_BUDGET` of picture bytes go in one file, and the finished file stays under
  `NOTEBOOK_EXPORT_MAX_BYTES` (a response must stay under Vercel's 4.5 MB): with lots of text it's rebuilt with fewer
  pictures (`buildNotebookDocxWithin`), and text alone too big is a 413 saying to export a page or print. Pictures left
  out, and WebP, get a line instead and the title page says how many. Links in the text are clickable. The file name is
  cut by whole characters (never half an emoji). **Print / Save as PDF** — `/notebook/print/n/[id]`
  and `/notebook/print/p/[id]` in the `(notebook-print)` route group (no app menus; print CSS, page breaks, every picture).
- Pages: `/notebook` (the outline: each notebook folds up — remembered per browser — with its pages, manager tools,
  export, and the latest entries), `/notebook/p/[pageId]` (desktop: the outline on the left; phones: "All notebooks" /
  "Jump to a page"; newest first or `?order=oldest`, 30 per screen), `/notebook/new`, `/notebook/n/[id]/edit`. No emails.

## Team calendar (`src/server/services/calendar.ts`, `/calendar`)

The season schedule: league meets, the ILT, scrimmages, competitions, outreach, team events, deadlines (`CalendarEvent`).
Everyone ACTIVE sees it; staff (`canManageCalendar` = `isStaff`) add, edit, and remove events. No emails.
An event has `startsOn` / optional `endsOn` (`@db.Date`, last day inclusive, at most 30 days after the first; 5 years back /
2 years ahead like fundraising — an edit may keep a date it already has) and optional `startTime` / `endTime` ("HH:MM", team
timezone; no start time = all day; an end time needs a start time and, on a one-day event, must be later; on a multi-day
event the times are the first day's start and the last day's end). Field rules live in `src/lib/calendar.ts`
(`checkCalendarEventFields`, client-safe); links get `https://` added. The edit form sends `version` (the `updatedAt` it
loaded): a stale save is a `ConflictError`, checked before the fields (a stale form with a field error still gets it);
the action revalidates anyway, so saving again replaces the other change.
Creates are rate-limited (60/hour/person). `sourceKey` marks events loaded from a season schedule by a data migration
(`20260927225500_season_schedule_2026_27`: the four Biobuzz league scrimmages, kind "League scrimmage") so loading again
never duplicates them; edits keep it, and `db:seed -- --reset` keeps them (it removes only events people added).
`getNextMeet(today, time)` = the first `CALENDAR_MEET_KINDS` event that isn't over — its last day is today or later (so a
tournament in progress counts), minus today's whose end time has passed (`time` = team timezone "HH:MM",
`timeInTimezone`; `eventIsOver`) — by first day then start time (all day first), plus the two after it — the calendar's
hero and Today's `NextMeetCard` (top of Today: "Next meet in N days"). While this season's ILT isn't on the calendar
(`isIltOnCalendar`: no ILT coming up or ended in the last 120 days) the hero says "Qualifying Tournament (ILT): date TBD".
A multi-day event with times shows "Starts …" / "Ends …" with their days (`multiDayTimedEnds`), never daily-looking hours.
`/calendar` has Month (`?month=YYYY-MM`; two-line 40px bars per day from `lg` up, where the per-day "+" is a mouse-only
shortcut; a dotted grid plus that month's list on phones and tablets), List (`?view=list`, upcoming) and Past
(`?view=past`, 100 most recent) views, filtered by `?kind=` (chips scroll sideways on phones, wrap from `sm`). "Add to my calendar" serves RFC 5545 files from `/calendar/export.ics` (events from a year ago on) and
`/calendar/[id]/event.ics` (`buildIcs`: CRLF, 75-octet folding, TEXT escaping, all-day as DATE with exclusive DTEND, timed
events converted to UTC with `zonedTimeToUtc`, UID `<id>@huskyteers-portal`) — signed-in ACTIVE users only, `text/calendar`,
`attachment`, `private, no-store`, `nosniff`.

## Meeting updates (`src/server/services/meeting-updates.ts`, `/updates`)

After every meeting each subteam writes what it did ("What we did", required), "Next time", and "Problems or help needed"
(`MeetingUpdate`: `meetingDate` `@db.Date` + `subteam`, no unique constraint — several people may write for the same
subteam and day, and each update shows its own author). You write for your own subteam; the captain, mentors, teachers, and
owners write for any (`meetingUpdateSubteams` / `canWriteMeetingUpdate`). Whoever wrote it, that subteam's leader, and
all-scope staff edit or remove it (`canEditMeetingUpdate`); moving it to another subteam also needs `canWriteMeetingUpdate`
for the new one (keeping its subteam is always fine). Everyone ACTIVE reads everything. The meeting date can't be in the
future (team timezone) or more than a year back (`src/lib/meeting-updates.ts`; an edit may keep its saved date). A save that
changes something sets `lastEditedAt/lastEditedById` ("Edited by … · 2 h ago"); one that changes nothing writes nothing.
The edit form sends `version` (the `updatedAt` it loaded): a stale save is a `ConflictError`, and the action refreshes the
page even when the save fails, so saving again replaces the other edit. Every save sets `updatedAt` explicitly (`ctx.now`, but
always at least 1 ms past the previous one), so the version moves even within one millisecond. A removal only deletes the
row as it was when permission was checked (same author, subteam, and `updatedAt`), else `ConflictError`. Creates are rate-limited
(`MEETING_UPDATE_RATE_LIMIT`, 30/hour), edits and removals 120/hour. The feed (`queries/meeting-updates.ts`) pages by
meeting day (`MEETING_DAYS_PER_PAGE` = 10, newest first), each day's updates grouped by subteam (three columns once the feed itself is `@4xl` wide — a container query, so
the sidebar counts; stacked below that, where the subteams nobody wrote for share one "No … update yet" line), with
`?subteam=` and `?who=mine` filters. Today shows `TodayUpdateNudge` on team days (attendance
schedule) or once someone wrote one for today; the attendance two-week report lists the period's updates
(`getMeetingUpdatesBetween`) and the meeting days (days attendance was taken) missing a subteam's update
(`missingMeetingUpdates`). `?focus=<id>` (`meetingUpdateFocusHref`: Today's links, the edit page's Back/Cancel) opens the feed
at an update. No emails.

### Services (mutations)

```ts
// src/server/services/things.ts
import { z } from "zod";
import type { ServiceContext } from "../context";
import { parseInput } from "../action";
import { ForbiddenError, NotFoundError } from "../errors";

const input = z.object({ title: text("Title", LIMITS.taskTitleMax) });

export async function createThing(ctx: ServiceContext, raw: unknown) {
  const data = parseInput(input, raw as Record<string, unknown>);   // throws ValidationError with fieldErrors
  if (!canDoIt(ctx.actor)) throw new ForbiddenError();
  const thing = await ctx.db.thing.create({ data: { ... } });
  ctx.notifier.notify({ type: "...", ... });                          // after the write succeeds
  return { id: thing.id };
}
```

- Signature: `(ctx: ServiceContext | PublicContext, raw: unknown)`. Validate **inside** the service with zod (so tests cover validation). Use helpers in `src/lib/validation.ts` (`text`, `optionalText`, `stringArray`, `checkbox`, `dateOnlySchema`, `emailSchema`, `idSchema`, `optionalEnum`).
- Use `ctx.now` (not `new Date()`) and `ctx.config` (not `process.env`) so tests are deterministic.
- Throw the typed errors from `errors.ts`; their messages are shown to users, so write them for humans.
- Multi-step writes → `ctx.db.$transaction(...)`.
- Emit notifications via `ctx.notifier.notify(event)` — never send email directly from a feature.
- Return small plain objects (ids), not raw DB rows.

### Queries (reads for pages)

`src/server/queries/<feature>.ts`, `import "server-only"`, use the `prisma` singleton, take the `Actor`, and **always apply the scope helpers**.
Select only needed columns; `take` a sensible limit (paginate at 50). Return plain serializable data (convert `@db.Date` with `dbToDateOnly`).

### Server Actions

In `src/app/(app)/<route>/actions.ts` with `"use server"` at the top:

```ts
export async function createThingAction(_prev: ActionState, formData: FormData): Promise<ActionState> {
  return runAction(async () => {
    const ctx = await getServiceContext();              // throws UnauthorizedError if not signed in/active
    const { id } = await createThing(ctx, formDataToObject(formData));
    revalidatePath("/", "layout");                      // refresh pages + nav badge counts
    redirect(`/things/${id}`);                           // optional; runAction re-throws redirects
  }, { success: "Saved.", formData });
}
```

- Every action: build the context, call a service, `revalidatePath("/", "layout")` after writes. No business logic in actions.
- Bound args are fine for ids: `action.bind(null, assignmentId)` — but the service must still re-check permissions from the DB.
- Action return values go to the browser: only `ActionState`.

### Pages & components

- Pages are Server Components. Guard every page: `requireActiveUser()` / `requireStaffUser()` / `requireAdminUser()` (the `(app)` layout already requires ACTIVE, but pages must still get the actor themselves and must do their own role checks).
- `params` / `searchParams` are Promises: `export default async function Page({ params }: PageProps<"/manage/tasks/[id]">) { const { id } = await params; }`. Use `notFound()` for missing/forbidden items the user shouldn't know exist.
- Set `export const metadata = { title: "..." }` on pages (title template adds " · Huskyteers Portal").
- Forms: client components with `useActionState(action, initialActionState)`, `<SubmitButton>` (pending state), `<FormMessage state={state} />`, per-field errors via `<Field error={state?.fieldErrors?.title}>`, and `defaultValue={state?.values?.title ?? initial}` so input survives validation errors.
- Use the UI kit: `Button/ButtonLink/buttonClasses` (size `icon` = 40px square icon button; `cn` only joins classes, so an override only wins if the kit leaves that property out — padding is left out when you pass your own `p-*`/`px-*`), `SubmitButton` (supports `confirm="Are you sure?"`), `Field/Input/Textarea/Select/CheckboxField`, `Card/CardHeader/CardBody`, `Badge/CountBubble`, `Alert`, `FormMessage`, `EmptyState`, `PageHeader`, `Avatar`, `ProgressBar`, `StatCard`, `LinkTabs`, `Pagination/parsePage`, `RichText` (user text; never `dangerouslySetInnerHTML`).
  Domain badges: `RoleBadge`, `SubteamBadge` (null = "Whole team"), `AccountStatusBadge`, `AssignmentStatusBadge`, `QuestionStatusBadge`, `PriorityBadge`, `DueBadge`; `UserChip`, `describeRole`.
- Icons: `lucide-react` (v1 names, e.g. `MessageCircleQuestionMark`, `CircleCheck`, `LoaderCircle`).
- **Mobile first**: most members use phones. Tap targets ≥ 40px, no horizontal page scroll at 375px wide (tables → stacked cards on small screens or `overflow-x-auto` wrappers), bottom tab bar occupies ~64px. A sticky bar at the bottom of the page (like Select mode's Remove bar) carries `data-sticky-action-bar`: `globals.css` then adds scroll padding so keyboard focus isn't hidden under it.
- Look & feel: brand green `brand-*`, neutral `ink-*`, white cards on `bg-canvas`, `font-display` (Oswald) for page titles only. Keep copy short, friendly, and specific.
- Empty states for every list. Loading: add `loading.tsx` only if a page is slow; forms already show pending.

## Resources (`src/server/services/resources.ts`)

A Resource is a link or a small uploaded file (`ResourceFile`, bytes in Postgres, ≤ `LIMITS.resourceFileMaxBytes` = 4 MB each and
`LIMITS.resourceStorageMaxBytes` in total; Server Action bodies are capped at 5 MB in `next.config.ts`, and Vercel rejects
requests over 4.5 MB, so don't raise the file limit).

- People with admin access (`canManageResources`) add resources that go live (APPROVED) and can edit/remove/pin anyone's.
- Everyone else's start PENDING, are only visible to them and reviewers (`canViewResource` / `visibleResourcesWhere`), and are
  approved or turned down (`reviewResource`, `canReviewResources`). A member's edit sends it back to PENDING.
- Files are served only by `src/app/(app)/resources/files/[id]/route.ts` with the headers from `src/server/resources/serve.ts`:
  text as `text/plain`, png/jpeg/gif/webp and PDF inline, everything else (HTML, SVG, …) as an `application/octet-stream`
  download; always `nosniff`, a sandboxing CSP (PDFs skip `sandbox`, which Chrome's PDF viewer refuses), and `no-store`
  (only poster files opt into browser caching, `immutable`).
  Windows executables/scripts are refused at upload (`BLOCKED_EXTENSIONS`). Never render uploaded content as HTML.
- Upload checks (`src/server/files/upload.ts`) and the storage cap (`src/server/files/storage.ts`) are shared with sponsor
  files and posters; any new kind of stored file must use `assertFileStorageRoom` so every file counts toward the same cap.
  "Full" messages start with `storageFullSentence(usage)` (how much is Resources files vs sponsor files, plus posters when
  there are any) and say who can free each (`posterCleanupSentence(usage)` adds who can remove posters). Usage is shown on Admin → Approvals ("File storage") and on each sponsor's file card (`getFileStorageUsage`).

## Notifications (email)

Services emit `NotificationEvent`s (see `src/server/notifications/events.ts`). `src/server/notifications/deliver.ts` decides recipients
(respecting each user's `emailOn*` preferences, skipping the person who caused the event) and sends via `sendEmail()`, which writes `EmailLog`.
Production sends run in `after()` so user actions never wait on SMTP.

| Event | Emitted by | Recipients (pref) |
|---|---|---|
| `question.asked` | questions | `recipientId` if set; else ACTIVE leaders of `subteam`; if subteam null → ACTIVE captains (`emailOnQuestion`) |
| `question.replied` | questions | staff replied → asker (`emailOnReply`); asker replied → recipient or subteam leaders/captains + staff who already replied (`emailOnQuestion`) |
| `task.submitted` | checklist | task creator if they can still review it; otherwise the first non-empty tier of reviewers: leaders of the task's subteam (whole-team task: of the submitter's subteam) → captains → admins (`emailOnSubmission`) |
| `task.reviewed` | tasks | assignee (`emailOnReview`) |
| `task.assigned` | tasks | the new assignees, except whoever made the change (`actorId`) (`emailOnAssigned`, default off) |
| `account.pending` | auth | everyone with admin access: ACTIVE owners, leaders, captain, mentors, teachers (`emailOnSignup`) |
| `account.approved` | admin | that user (always) |
| `password.reset` | auth/admin | that user (always) |
| `password.changed` | auth/settings | that user (always, security notice) |
| `resource.submitted` | resources | ACTIVE owners + leaders of the member's subteam (captains if the member has no subteam or it has no active leaders), never the member (`emailOnResource`) |
| `resource.reviewed` | resources | the member who shared it (`emailOnReview`) |

`question.asked` / `question.replied` are also posted, in full, to a leaders-only Discord channel when `DISCORD_WEBHOOK_URL` is set (`src/server/notifications/discord.ts`; one-way, logged in EmailLog as `to = "Discord"`, `allowed_mentions` empty so user text can't ping anyone).
